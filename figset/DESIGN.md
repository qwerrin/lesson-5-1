## 2. 目的とスコープ

### 2-1. 目的

ShareX が吐く**タイムスタンプ名の生スクショ**を、記事に貼れる**図版セット**
（連番 PNG ＋ 対応表 README ＋ 貼り付け用 HTML 断片）へ変換する。

### 2-2. やること / やらないこと

| やること | やらないこと |
|---|---|
| 原本の収集とハッシュ台帳化 | 画像の加工・トリミング・黒塗り |
| 画像を読んで**何が写っているか**を判定 | ShareX 自体の設定変更 |
| 連番の割付（**2系統の番号を両方持つ**） | 記事本文の生成 |
| 対応表 README の生成 | 記事プラットフォームへの自動投稿 |
| 記事貼り付け用の `<img>` 断片の出力 | 撮影そのもの（`shots.py` の担当） |
| **対応表の主張が画像に実在するかの照合** | 没カットの自動削除（**消さない**・印を付けるだけ） |

### 2-3. 既存の道具との境界

`task3/tools/shots.py`（284行）は**撮影の実行係**で、コマンドを走らせて
「この絵が何を証明するか」の帯を画面に出す。**撮るところまでが `shots.py`**。

`figset` は**撮った後**を受け持つ。両者は入れ替えない。

## 3. ★ 穴分析：何を見ていないか（実装前に出す）

### 3-1. 取得していないもの

| | 見ていないもの | なぜ問題か |
|---|---|---|
| **H1** | ShareX のファイル名は**タイムスタンプだけ** | 何を写したかがファイルから取れない。人間の記憶が唯一の索引になっている |
| **H2** | **撮影順 ≠ 記事順**（実測で 1→01, 2→04, 3→06, 6→02, 8→03） | *並び順を意味に使えない*。再生リストの N番目＝N話がズレた件と同じ型 |
| **H3** | **没カットが混じる**（10枚中2枚） | 没と採用はファイル属性では区別できない。撮り直しの前後を取り違えると古い絵が記事に載る |
| **H4** | 撮り直すと**ほぼ同じ絵**が2枚できる | サイズもハッシュ近傍も当てにならない。中身で見分けるしかない |
| **H5** | 絵の中の**数字**（★8件中2件 / 119/119 / 58項目）はファイルからは読めない | 対応表に書いた数字が絵と合っているかを機械で言えない |
| **H6** | ShareX は**月フォルダで分断**する | task3 の8枚は `2026-09` 内だが 09-14 と 09-15 にまたがった。月をまたぐ課題では2フォルダになる |
| **H7** | 保存先そのものが**設定依存** | 環境変数やユーザー名から組み立てない（教訓 `detector-inputs-must-not-come-from-env`：`USERNAME` が実際のユーザー名と違い、空なら黙って検査ゼロになった） |
| **H8** | 画像の**撮影時のシェル状態**（プロンプト・タイトルバー） | `cls` は履歴しか消さない。枠は毎行ホームのパスを出す。**自分の出力を grep しても見つからない** |
| **H9** | 記事に貼った後の**実際の表示状態** | ファイルが存在することと、記事で表示されていることは別 |

### 3-2. 正常終了しても欠落するケース

| | 欠落 | 検査の当て |
|---|---|---|
| **M1** | 対応表に行があるのに**画像が無い**（撮り忘れ） | 行と実ファイルを双方向で突き合わせる |
| **M2** | 画像があるのに**対応表に行が無い**（貼り忘れ） | 同上。**片方向だけ検査すると必ず漏れる**（教訓 `consumers-do-not-prove-producers`：読む側は付いていて、付ける側だけ無かった） |
| **M3** | 記事に貼ったが**表示されていない**（`naturalWidth === 0`） | 公開後に実寸まで確認する（課題3 で実施済みの手順を取り込む） |
| **M4** | 絵の中の数字と対応表の数字が**ズレる** | 数字を抽出して照合。**照合0件を「一致」にしない**（`verify_doc` の 5-O と同型） |
| **M5** | **秘匿情報が写る**（ホームのパス・本名・トークン） | 課題3 で実際に踏んだ。`04-meet.png` は表示名を黒塗りした実績あり |
| **M6** | 同名保存で**前の画像を上書き** | 台帳にハッシュを残し、同じ名前でハッシュが変わったら警告 |
| **M7** | **原本が消えている**（ShareX 側を掃除した） | 物差しが無い状態で「一致」と言わない。**確認不能**に倒す |
| **M8** | 画像を**読めなかったのに「問題なし」に倒す** | *読めなかったこと と 問題なかったこと は別*（`verify_doc.py` の「値が返らなかった項目を OK にしない」をそのまま移す） |
| **M9** | 判定が**1枚も走らなかった**のに全体は成功 | 対象0件を成功にしない（`all_ok` の「空を真にしない」） |
| **M10** | ★ **秘匿情報の検査を外部 API に聞いた時点で、もう送っている** | 2026-09-19 の疎通確認中に気づいた。M5 を「画像を Gemini に読ませて判定する」で実装すると、**トークンが写った画像をトークンごと送ってから「写っていますね」と返ってくる**。*検査は、送る前にローカルで走らせなければ意味がない*（第3-3節） |

### 3-3. ★ 検査の順番が、検査の意味を決める（M10・2026-09-19）

**この道具は画像を外部（Gemini API）へ送って中身を判定する。**
ということは、**送った時点で、写っているものは全部外に出ている**。

だから M5（秘匿情報の写り込み）を「Gemini に聞いて判定する」で実装すると、
*トークンが写った画像をトークンごと送ってから「写っていますね」と教えてもらう*
という順番になる。**検査は通るが、守れていない。**

```
    ✗ 送る → 聞く → 「パスが写っています」     ← もう漏れている
    ○ ローカルで見る → 通ったものだけ送る → 聞く
```

**設計に落とすと、処理の流れに段が1つ増える**（第5章の 2. `guard`）:

| 段 | どこで走るか | 何を見るか |
|---|---|---|
| `guard` | **ローカルのみ。外に出さない** | 既知の秘匿文字列（ホームのパス・利用者名・トークンの形）が画像に写っていないか |
| `classify` | 外部 API | `guard` を通った画像だけ |

**`guard` に何を使うかは未確認（U3）。** ローカル OCR が要るか、
それとも「疑わしい画像は送らず、人間に見せて判断させる」で足りるか。
*外に出す前に止める、という順番だけは動かさない。*

> **これは「検知することと守られていることは別」の新しい形。**
> vault のバックアップ（`OPEN_QUESTIONS` B6）では *検知はできているが守られていなかった*。
> ここでは **検知そのものが漏洩の経路になる**。

## 5. 処理の流れ

```
1. collect   原本を集める → SHA-256 で台帳化（没も含めて全部載せる）
2. guard     ★ ローカルだけで秘匿情報を見る。ここを通らない画像は外へ出さない
3. classify  画像を読んで「何が写っているか」を判定（← 外部 API）
4. layout    figs.yaml と突き合わせて番号を割り付ける（採用/没を決める）
5. emit      docs/ へコピー・README・figs.html を生成
6. verify    ★ 対応表の主張が、画像に実在するかを照合（← 外部 API）
```

**5 と 6 を分ける。** 書けたことは、読み戻せることの証拠にならない
（教訓 `write-is-not-readback`）。

**2 を 3 より前に置く。** 順番が逆になった瞬間、この道具は
*秘匿情報を送ってから「送ってはいけないものでした」と教える道具*になる（3-3・M10）。
**流れ図に段として出しておくのは、コードの奥に隠すと順番がいつか入れ替わるから。**

## 6. ★ 照合の設計 — ソース側を開く

課題2（5-1-1）の講評:

> ただ商品リンクにアクセスし、**取得した情報が正しいかどうかまで確認**して
> スクショをとれるとより良いですね！

この指摘は **3回続いた**（教訓 `assignment-verify-against-the-source`）。
課題3 で `verify_source.py` を作って答えた結果、**課題3 の講評では消えた**。

`figset` での答え:

| 見る相手 | 何をするか |
|---|---|
| **出力側**（README・figs.html） | 行と実ファイルの双方向照合・HTML の `src` が実在するか |
| **ソース側**（画像そのもの） | 対応表の「この絵が証明すること」に書いた**数字を抽出**し、**画像を開いて**その数字が中に実在するかを突き合わせる |

**README を読み返すのは照合ではない。ソースは画像。**

### 6-1. 判定を安全側に倒す規則

1. **読めなかった項目を OK にしない**（M8）
2. **照合0件を「一致」にしない**（M4・M9）
3. **原本が無いものは「不一致」ではなく「確認不能」**（M7）。
   誤検知で毎日鳴ると読まれなくなる（教訓 `silence-has-two-meanings` の裏面）
4. **件数を必ず出す**。「問題なし」だけでは、何件見たかが分からない

## 8. テスト方針

`scripts/` の手順（`CLAUDE.md`）をそのまま適用する:

1. **テストを先に書いて RED を確認する**（後から書くと期待値を実装から作ってしまう）
2. GREEN にする
3. **わざと壊して、テストが落ちることを確認する**（`tools/mutate.py`）
4. **素通り0件**になるまでテストを足す

### 8-1. とくに注意すること

- **判定のテストだけでは足りない。** 収集（`collect.py`）がその項目を実際に
  読んでいるかは、データクラスを手で組むテストでは1件も確かめられない
  （`vault_core` で実際に踏んだ：`state` の読み取りを消してもテスト81件が全部通った）
- **ミューテーションは効いていないと素通りに見える**（`a-mutation-must-actually-mutate`）。
  置換先が無い箇所は SKIP として数え、SURVIVED と区別する
- **期待値に「今日」を使わない**（`today-as-expected-value-hides-date-bugs`）。
  撮影日は固定値で書く
- **画像のテストは実物を1枚通す。** ダミーのバイト列だけだと、
  デコードのバグが隠れる（`stringio-hides-decoding-bugs` と同型）

| | クセ | 実装での扱い |

> 実装時にテスト用の図版で数を増やす。**#5 の形（わざと違う数字を投げる）を
> 単体テストに常設する**——これは *壊して確かめる* をそのまま検査に据えたもの。

| **U4** | ShareX の保存先を**どこから読むか** | 設定ファイルに書かせる（H7）。ShareX の設定を読みに行かない |
| **U5** | 課金と実行時間 | 1課題あたり10枚前後。1枚あたりのコストと所要を実測してから cron 化を判断する |
| **U6** | `guard.py` に外部通信が無いことを**どう証明するか** | 「呼んでいない」は主張であって証拠ではない。**通信を塞いだ状態でテストを通す**などの当てを決める |

## 10. 発展アイデア（誰に・いつ・どんなメリットが）

> **この形式は 5-1-1 課題4 の講評で指定された**（「どんな人に・どんな時に・どんなメリットが」）。
> さらに 課題9 の講評で「**実装してスクショを載せる**」が追加された。
> **考える → 実装する → そこからさらに考える** を回す。

| # | アイデア | 誰に | どんな時に | どんなメリットが |
|---|---|---|---|---|
| 1 | **秘匿情報の写り込み検査を単体で回す** | 技術記事を書く人 | 公開ボタンを押す前 | ホームのパス・本名・トークンが写った画像を、公開前に止められる。*漏れるのは枠のほう*で、自分の出力を grep しても見つからない |

## 11. 記事に載せる図版の当て

**`figset` の記事の図版を、`figset` 自身で作る。**
これが一番強いデモになる（道具が自分に効くことの証明）。

| 図版 | 何を写すか | この絵が証明すること |
|---|---|---|
| 01 | 台帳（`figset.json`）の一覧 | 10枚のうち**2枚が没**であることが、ハッシュ付きで機械に見えている |
| 02 | 番号の割付結果 | **撮影順と記事順が違う**ことが表で出る |
| 03 | ★ ソース側照合 | 対応表の数字が**画像の中に実在するか**。件数を絵に入れる |
| 04 | `guard` が止める画面 | わざとパスを写した1枚が、**外へ送られる前に**止まる（3-3・M10） |
| 05 | 双方向照合（M1/M2） | 行だけ／画像だけ、どちらの片落ちも検出する |
| 06 | ★ **わざと違う数字を投げた照合** | 対応表に `117` と書いて画像が `119` のとき、**不一致と言える**。*照合ツールが主張に同意してしまわないこと自体を絵にする*（9-1 の #5） |
| 07 | ミューテーション | 素通り0件 |

**対にして読ませる**（課題2 の講評が求めた形）:

| 対 | 言えること |
|---|---|
| 03（ソース側） ＋ 05（出力側） | 同じ `verify` でも**見ている相手が違う** |
| 01（没2枚） ＋ 02（順序の食い違い） | *並び順を意味に使えない* |
