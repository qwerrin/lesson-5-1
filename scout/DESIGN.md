## 2. ★ 最初に決めること：取ってよいかを確かめる

**この vault には前例がある。**

`NoteScraperDaily`（毎朝9時に note.com の記事を取得して CSV を吐く）を
2026-08-21 に止めた。決め手は「使っていない」ことではなく、
**`note_scraper.py` 自身の docstring が
「robots.txt で `/api/*` は Disallow」「商用・自動化目的での大量利用は行わない」と
書いていた**ことだった。

したがって `scout` は:

1. **取得元ごとに「何を根拠に取ってよいか」の表を設計に持つ**（下表）
2. **公式に提供されている手段（API / RSS）だけを使う**
3. 公式手段が無い取得元は、**取りに行かない**（設計から落とす）
4. 取得間隔・件数の上限を設定ファイルに明示し、既定を控えめにする

### 2-1. 取得元と「取ってよい根拠」（2026-09-19 に確認）

| 取得元 | 使う手段 | 認証 | 上限 | 規約の自動アクセス条項 |
|---|---|---|---|---|
| **Qiita** | REST API v2（`qiita.com/api/v2/docs` で文書化） | **GET は不要** | **認証あり 1000回/時・なし 60回/時**。超過は **429**（公式ドキュメントに明記） | **無い**。第18条は「私的使用の範囲を越えて使用することはできません」 |
| **Zenn** | RSS フィード（`zenn.dev/topics/<topic>/feed`） | 不要 | **明記なし** → こちらで控えめに決める | **無い**。ただし利用者コンテンツの「**無断で転載または二次配布**」は禁止 |

**表に書けない取得元は対象にしない。** 「たぶん大丈夫」で足さない。

### 2-2. Zenn がフィードを提供していることの根拠

トピックページの HTML が**サイト自身の宣言として**持っている:

```html
<link rel="alternate" type="application/rss+xml"
      title="Claude Codeの投稿フィード"
      href="https://zenn.dev/topics/claudecode/feed">
```

**推測ではなく、サイトが「ここにフィードがある」と書いている。**
Zenn には公式 API は無い（FAQ にも利用規約にも記載が無い）。

### 2-3. Qiita の robots.txt をどう読んだか（**判断の記録**）

Qiita の `robots.txt` は次のようになっている:

```
User-agent: *
Disallow: /api/*
...
Allow:    /api/*/docs$
```

**`/api/*` が Disallow されている。** これは `NoteScraperDaily` を止めたときと同じ形に見える。
だが**止めない**と判断した。理由:

| | note.com（**止めた**・2026-08-21） | Qiita（**進める**） |
|---|---|---|
| robots.txt | `/api/*` Disallow | `/api/*` Disallow |
| **規約の自動利用条項** | **「商用・自動化目的での大量利用は行わない」と明記** | **条項が無い** |
| **上限の明示** | 無し | **1000回/時・60回/時・429 を公式ドキュメントに明記** |

`robots.txt` は**クローラ（URL を辿って索引する側）への指示**であり、
Qiita は同じファイルで `Allow: /api/*/docs$` としてドキュメントだけ索引を許している。
そのうえで**回数の上限を数字で公開し、超えたら 429 を返すと明言している**。
*上限を明示して提供する行為は、上限内での利用を想定している。*

**これは解釈なので、ここに書き残す。** 前提が変わったら（規約に条項が増えたら）読み直す。

**守る側の設計**: 既定を**認証なしの上限 60回/時 の 1/10 以下**に置く。
認証ありの 1000 は使わない——*上限いっぱいまで使わなければ、解釈が多少ずれていても害が出ない*。

### 2-4. ★ 取得元によって、できることが違う（2026-09-19 の実測で判明）

**この設計の山場。** 2つの取得元は「記事を返す」点では同じだが、**返すものが違う**:

| | Qiita | Zenn |
|---|---|---|
| 検索 | `query` で絞れる（`tag:` `created:>=` `stocks:>` `-tag:` `title:` `body:`） | **無い**。トピック単位のフィードのみ |
| 件数 | `per_page` ≤100 × `page` ≤100 | **20件固定・遡れない** |
| **本文** | **`body`（Markdown 全文）＋ `rendered_body`（HTML）** | **取れない**——`description` が **300字で打ち切り**、`content:encoded` が無い |
| 日時 | ISO 8601 | **RFC822 / GMT** |
| 返す項目 | `title` `url` `body` `created_at` `updated_at` `tags[]` `likes_count` `stocks_count` `page_views_count` `user.id` | `title` `link` `description`(300字) `guid` `pubDate` `enclosure` `dc:creator` |

**帰結: Zenn では第6章のソース側照合が成立しない。** 物差しになる本文が無い。

だから**取得元ごとに、できることの範囲を分ける**:

| 取得元 | 収集 | 要約 | **ソース側照合** |
|---|---|---|---|
| Qiita | ○ | ○ | **○（本文がある）** |
| Zenn | ○（**見出し ＋ リンクのみ**） | **×** | **×（物差しが無い）** |

**規律: 照合できないものは要約しない。**

要約は「本文を読んで縮めたもの」という主張である。本文を持っていないのに要約を出せば、
*それは要約ではなく推測*になる。教訓 `search-summaries-blend-sources`
（出典として書こうとした一文が、その記事に無かった）が起きるのは、まさにこの状況。

Zenn は**新着の見出しとリンクを並べるだけ**にする。読むのは本人がブラウザで開いて読む。
記事本体を取りに行かない理由は2つ——規約が「無断で転載または二次配布」を禁じていること、
そして**取りに行けば負荷を自分で制御しなければならない**のに、Zenn 側は上限を明示していないこと。

> **この非対称は、要件定義の H10（本文が全部取れているか見ていない）が
> 実装前に実物で当たったもの。** 書いていなければ、Zenn の要約を作って
> 「なぜか出典が合わない」を後から踏んでいた。

## 3. ★ 穴分析：何を見ていないか（実装前に出す）

### 3-1. 取得していないもの

| | 見ていないもの | なぜ問題か |
|---|---|---|
| **H1** | 検索は**見つかったものしか返さない** | 取りこぼしは沈黙する。「無かった」と「探せていない」が出力上は同じ |
| **H2** | **0件と「取れなかった」が同じ見た目** | 提供側は「無い」を成功として返す（教訓 `absence-can-return-success`：HTTP 200 ＋ 0件。404 も例外も出ない） |
| **H3** | **公開日と取得日は別物** | 古い記事が「新着」に化ける。更新日と公開日も別 |
| **H4** | 要約は**元記事に無いことを書く** | 教訓 `search-summaries-blend-sources`：出典として書こうとした一文が、その記事に無かった |
| **H5** | URL を正規化しないと `?utm_source=` 違いが**別物になる** | 同じ記事を何度も取り込む |
| **H6** | 取得元ごとに**日時の形式が違う** | **実測で確定（2026-09-19）**: Qiita は **ISO 8601**、Zenn の `pubDate` は **RFC822 の GMT**。vault は JST。**日付の物差しを2本置かない**（教訓 `one-date-basis-per-output`：UTC のログとローカル日付を先頭一致で比較して、cron の実行時刻が安全帯だったため本番でも出なかった） |
| **H7** | 取得元の**利用規約・robots.txt はコードからは分からない** | 第2章。人間が確認して表に書く |
| **H8** | **捨てたものは記録されない** | 「読む価値なし」と判定した記事が消える。判定の良し悪しを後から検証できない |
| **H9** | 自分が**既に読んだ／既に vault にある**ものを見ていない | 重複を持ってくる。`vault_triage` の台帳と突き合わせる必要がある |
| **H10** | 本文が**全部取れているか**を見ていない | **実装前に実物で当たった（2026-09-19）**: Zenn のフィードは `description` が **300字で打ち切り**。*一部しか無いことと、短い記事であることは、長さだけでは区別できない* |
| **H11** | Qiita の `created:>=` は**日付までで、時刻が無い** | 増分取得が**日単位**にしかできない。前回実行と同じ日に走らせると**同じ記事を必ず再取得する**。→ 重複判定（`dedupe`）は任意の最適化ではなく**必須の部品** |
| **H12** | Zenn のフィードは**20件固定で遡れない** | 1日に21件以上出たトピックは、**取りこぼしが起きても何も言わない**。H1（見つかったものしか返さない）の具体形 |
| **H13** | Qiita は `page` 最大100 × `per_page` 最大100 | **1万件より深くは辿れない**。広いクエリを投げると静かに頭打ちになる |

### 3-2. 正常終了しても欠落するケース

| | 欠落 | 検査の当て |
|---|---|---|
| **M1** | レート制限で途中で切れたのに、取れたぶんだけで「完了」 | 期待件数と取得件数を突き合わせ、打ち切りを**明示的に記録**する |
| **M2** | 取得元1つが死んでも、**他が生きていれば全体は成功に見える** | 取得元ごとに成否を持つ。1つでも失敗したら全体を成功にしない |
| **M3** | 認証切れが 401 ではなく**空配列**で返る | H2 と同じ。**0件は別経路で数える**（教訓 `zero-results-need-a-second-path`：実装が正しいのと「別のアカウントを見ている」が出力上まったく同じ） |
| **M4** | 重複判定が効きすぎて**新しい記事を捨てる** | 捨てた理由を台帳に残す（H8）。捨てた件数を必ず出す |
| **M5** | 本文が一部しか取れていないのに要約が作られる | 取得した本文の長さを記録し、極端に短いものを警告 |
| **M6** | 保存はできたが **Obsidian から見えない** | frontmatter を書いた後に**読み戻して**パースできることを確認（`write-is-not-readback`） |
| **M7** | **沈黙が2つの意味を持つ** | 「今日は良い記事が無かった」と「収集が死んだ」が同じ無音（教訓 `silence-has-two-meanings`）。**週1の生存通知**で確定させる |
| **M8** | 要約が**読めなかった記事**を「問題なし」に倒す | 読めなかったこと と 問題なかったこと を分ける |
| **M9** | **1件も処理しなかった**のに成功 | 対象0件を成功にしない |

### 3-3. この章の使い方

`figset` と同じ。**H1〜H10 / M1〜M9 はそのままテストの一覧**になる。
塞がなかったものは「承知で残した」と理由付きで書く。

## 4. 入力と出力

### 4-1. 入力

| | |
|---|---|
| 取得元 | **Qiita ＋ Zenn**（第2章の表に載っているものだけ） |
| 検索条件 | `topics.yaml` — 追いたいトピック。**取得元ごとに書き方が違う**ので両方持つ（Qiita は `tag:` などの検索式、Zenn は**トピックのスラッグ**） |
| 期間 | 前回実行日以降（台帳に記録）。**Qiita の `created:>=` は日付までなので、同日の再取得は必ず起きる**（H11）。**初回は `--since` を必須にする** |
| 上限 | 取得元ごとの1回あたり件数上限とリクエスト間隔（既定は控えめ・第2章 2-3） |

**`topics.yaml` が取得元ごとに分かれるのは、避けられない非対称**（2-4）。
「トピック名」という共通の抽象を被せると、**両方の説明が嘘になる**
——Qiita 側は検索式、Zenn 側は URL のスラッグで、**別物である**。
（課題4 で Zoom と Google の認証に共通の抽象を被せなかったのと同じ判断）

### 4-2. 出力

| | |
|---|---|
| 収集ノート | `01_Inbox/YYYY-MM-DD-scout.md`（**日次1ファイル・追記**） |
| 台帳 | `scout/state/seen.json` — 正規化 URL・公開日・取得日・採否・捨てた理由 |
| 通知 | 決定した件数のサマリ（**0件でも送る**。M7 対策） |

**着地先を `01_Inbox/` にする理由**（`CLAUDE.md` の規則にそのまま従う）:

> **raw と compiled を混ぜない。** `Clippings/` と `01_Inbox/` は raw の置き場で、
> そこから必要なものだけを `05_Knowledge/` へ昇格させる。

自動収集は raw なので `01_Inbox/` で受ける。
`clipbot.py` が `01_Inbox/YYYY-MM-DD-clips.md` へ書くのと**同じ形**にする。

## 5. 処理の流れ

```
1. fetch     取得元ごとに記事一覧を取る（取得元ごとに成否を持つ）
2. dedupe    URL を正規化して、台帳・vault と突き合わせる  ← H11 により必須
3. rank      読む価値でスコアを付ける（捨てた理由も残す）
4. split     ★ 本文を持つもの／持たないものに分ける
                ├ Qiita（body あり） → 5 へ
                └ Zenn（body なし）  → 7 へ（見出し＋リンクのみ）
5. summarize 要約する
6. verify    ★ 要約の主張が、本文に実在するかを照合
7. emit      01_Inbox/ へ追記 → 読み戻してパースできることを確認
8. notify    件数のサマリを送る（0件でも送る）
```

**6 を 5 と分ける。** 要約器に「正しく要約したか」を聞かない。
*一貫性の検査は、正しさの検査ではない*（課題3 で実測した形）。

**4 を独立した段にする。** 「本文があるか」で経路が分かれることを、
コードの奥ではなく**流れの図に出す**。ここを暗黙にすると、
将来 Zenn に本文があると思い込んだ誰か（＝半年後の自分）が要約を通してしまう。

## 6. ★ 照合の設計 — ソース側を開く

課題2（5-1-1）の講評が求めたのは「取得した情報が正しいかどうかまで確認」。
**同じ指摘が3回続いた**（教訓 `assignment-verify-against-the-source`）。

`scout` での答え:

| 見る相手 | 何をするか |
|---|---|
| **出力側**（Inbox のノート） | frontmatter が読み戻せるか・リンクが実在するか・件数が合うか |
| **ソース側**（記事本文） | 要約に書いた**引用・数字・固有名詞**を抜き出し、**本文を開いて**そこに実在するかを突き合わせる |

**要約を読み返すのは照合ではない。ソースは本文。**

> **この章が効くのは本文を持つ取得元だけ**（＝現状は Qiita のみ。2-4）。
> Zenn は本文が無いので**要約を作らず、したがって照合する対象も無い**。
> *照合できないものを要約しない*ことで、「照合していない要約」が1件も生まれない状態を作る。

### 6-1. 判定を安全側に倒す規則

1. **本文が取れなかった記事の要約を「照合済み」にしない**（M8）
2. **照合0件を「一致」にしない**（M9）
3. 本文が**極端に短い**ときは「確認不能」に倒す（M5）
4. **件数を必ず出す**。「N件中M件が本文に実在」の形にする

### 6-2. 出典の扱い

- 引用は**本文から取った文字列そのもの**だけを使う。要約器に書かせた引用は使わない
- 一致しなかった主張は**消さずに印を付ける**。消すと「なぜ落としたか」が消える

## 7. ファイル構成（機能ごとに分割）

```
scout/
  DESIGN.md          この文書
  topics.yaml        追いたいトピック
  sources.yaml       取得元と「取ってよい根拠」（第2章の表）
  fetch.py           取得（取得元ごとに成否を持つ）
  dedupe.py          URL 正規化・台帳/vault との突き合わせ
  rank.py            選別（捨てた理由を残す）
  split.py           ★ 本文を持つもの／持たないものに分ける（2-4）
  summarize.py       要約（**本文を持つものだけ**）
  verify_source.py   ★ ソース側照合
  emit.py            01_Inbox/ への追記と読み戻し
  notify.py          サマリ通知（0件でも送る）
  cli.py             入口
  state/seen.json    台帳
  tests/
  tools/mutate.py
```

**`verify_source.py` という名前を課題3 と揃える。**
同じ仕事をするものは同じ名前にする（対象が議事録から記事本文に変わっただけ）。

## 8. テスト方針

`figset` と同じ（`CLAUDE.md` の `scripts/` 手順）。
RED → GREEN → **わざと壊して落ちることを確認** → 素通り0件。

### 8-1. とくに注意すること

- **テストの宛先を隔離する**（教訓 `isolate-outbound-destinations-in-tests`）。
  `notify.py` のテストで**本番の宛先へ実際に配達しない**。
  *送ったものは取り消せない*
- **外部 API はモックだけで済ませない**（`mocked-tests-hide-integration-bugs`）。
  実物を1回叩く経路を別に持つ（`--probe`）
- **日付の期待値に「今日」を使わない**（`today-as-expected-value-hides-date-bugs`）
- **0件のケースを必ずテストに入れる**（H2・M3・M9）。
  *正常値が「空」の欄はバグが静かな側に倒れる*

## 9. 疎通確認（決着したもの／まだのもの）

**実装の前に1件ずつ潰す。**

### 9-1. 決着したもの（2026-09-19）

| | 何を確かめたか | 結果 | 出どころ |
|---|---|---|---|
| **U1** | Zenn に公式の取得手段があるか・利用条件は何か | **API は無い。RSS はある**（`zenn.dev/topics/<topic>/feed`）。規約に自動アクセス条項は無いが「無断で転載・二次配布」は禁止 | トピックページの `<link rel="alternate">` ／ Zenn 利用規約 ／ FAQ |

## 11. 記事に載せる図版の当て

**`figset` で作る。** 2本目の記事の図版を1本目のツールで生成することで、
*2本が繋がっていること*を絵で見せられる。

| 図版 | 何を写すか | この絵が証明すること |
|---|---|---|
| 01 | `sources.yaml` と取得元の表 | **取ってよい根拠を先に書いた**こと。`NoteScraperDaily` を止めた前例への答え |
| 02 | 取得結果（取得元ごとの成否） | 1つ死んでも全体が成功にならない（M2） |
| 03 | 0件のときの出力 | **0件と「取れなかった」が区別されている**（H2・M3） |
| 04 | ★ ソース側照合（Qiita） | 要約の主張が**本文に実在するか**。件数を絵に入れる |
| 05 | ★ **Zenn が要約段をスキップする画面** | *本文が無いものは要約しない*。経路が分かれていることが見える（2-4・H10） |
| 06 | 捨てた記事の台帳 | 捨てた理由が残っている（H8） |
| 07 | ミューテーション | 素通り0件 |

**対にして読ませる**:

| 対 | 言えること |
|---|---|
| 04（Qiita・照合あり） ＋ **05（Zenn・要約なし）** | **同じ「記事収集」でも、取得元が返すものが違えば、できることが違う**。*照合できないものは要約しない* |
| 04（ソース側） ＋ 要約の見た目 | *要約が自信を持って書いた一文が、本文に無いことがある* |
| 03（0件） ＋ 02（取得元の成否） | **無音の意味が2つある**のを、出力で分けている |
