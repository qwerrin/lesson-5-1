# 課題1 Slack の情報を取得・要約して LINE に送るツール

> Slack のチャンネルから情報を取得し、必要に応じて要約し、LINE に送信するシンプルなツールを作成する。
> **目的**: 重要な情報を LINE で受け取り、見逃しを防ぐ仕組みを実現。
> **ゴール**: 指定チャンネルのメッセージを自動取得 → LINE に要約メッセージを送るプロトタイプを完成させる。
> 【ヒント】Slack API のメッセージ取得エンドポイント、要約に使う LLM API、LINE Messaging API の送信例など、
> まずは Claude Code と要件を整理してから着手しましょう。（要件の原文ママ・2026-08-29 に講座サイトで確認）

## 「見逃しを防ぐ」は、順番でできている

この課題の目的語は「見逃し」である。**見逃しは例外を出さない。** 件数が減るだけで、
受け取る側からは「投稿が無かった日」と区別が付かない。だから設計の芯は全部
「静かに減らない」ことに向いている。

いちばん効いているのは**処理の順番**である。

```
読む → 要約 → 送る → 送信が成功したら位置を進める
                        ^^^^^^^^^^^^^^^^^^^^^^^^
```

最後の1手が最後にあることだけが、取りこぼさないことを支えている。途中で落ちた回は
位置が進まないので、次回また同じ範囲を読む。**重複はするが落とさない**（at-least-once）。
逆にすると、送信に失敗した範囲が二度と読まれない。

| 落ちた場所 | 位置 | 次回 |
|---|---|---|
| Slack の読み取り | 進まない | 同じ範囲を読み直す |
| 要約 | 進まない | 同じ範囲を読み直す |
| 送信 | 進まない | 同じ範囲を読み直す（**重複して送る**） |
| 送信の後 | **進む** | 続きから |

## 資格情報は `.env` に一本化した

Section 4-3 では渡し方が割れていた（課題4〜8は環境変数、課題9だけ `.env`）。
ここでは**3つとも `.env`** にする。理由は好みではなく、**環境変数が共有の名前空間だから**である。

2026-08-17、課題7のために `SLACK_BOT_TOKEN` を User スコープの環境変数へ置いた。
同じ PC に常駐していた別のシステムがそれを「Slack を使う」判定に読み、接続に必要な
別のトークンが無いまま起動しようとして落ちた。**そのシステムの定期実行が約2日間まるごと止まった。**
設定は1文字も触っていない。

`.env` はリポジトリの中で閉じているので、この形の巻き添えが起きない。

## 公式リファレンスで確認した罠（2026-08-29）

| 仕様 | 原文 | 効き方 |
|---|---|---|
| `oldest` は**排他** | 「Only messages **after** this Unix timestamp will be included」 | 前回の最新 ts を渡せば、その1件は重複しない |
| `inclusive` の既定は false | 「Include messages with `oldest` or `latest` timestamps. Ignored unless either timestamp is specified」 | **使わない**（下記） |
| **`limit` は best-effort** | 「Fewer than the requested number of items may be returned, **even if the end of the conversation history hasn't been reached**」 | ⚠️ 終わりを決めてよいのは `next_cursor` だけ |
| ページング | `response_metadata.next_cursor` | 空になるまで辿る |

**`limit` の一文がいちばん危ない。** `len(messages) < limit` を「終わりまで読んだ」と
解釈する実装は、相手が少なく返した回だけ静かに取りこぼす。件数では終わりを決めない。

### `inclusive` を使わない理由

包含にすると**毎回1件重複**し、要約に同じ発言が繰り返し混ざる。一方、排他でも
取りこぼしは起きない——前回の最新 ts **より後**を取るので、その ts の発言はすでに読んでいる。

取りこぼし対策は別の場所で作る（上の「順番」）。**同じ目的を2箇所で守らない。**

## `subtype` は「残す側」に倒す

除外するのは `channel_join` / `channel_leave` **だけを名指し**する。
「subtype があるものは全部捨てる」と書くと `bot_message` や将来増える種類まで落ちるが、
**知らないものを黙って捨てる向きは「見逃しを防ぐ」という目的そのものに反する**。

そのうえで、**捨てた件数は種類別に数えて残し、LINE の本文にも出す**。
「3件」と書いてあるのに Slack を見たら5件ある、という食い違いを受け取る側が自力で解けるようにする。

## 発展：スレッドの返信も読む（2026-09-04）

課題9の講評で「発展アイデアは考えるだけでなく実装して確かめる」と言われたので、
**アイデアを1つ実装した**。選んだのは機能を足す発展ではなく、**穴を塞ぐ発展**である。

### 公式が明言していないので、実測で閉じた

`conversations.history` がスレッドの返信を返すのかは、公式リファレンスに書いていない。
「返信は `conversations.replies` を使え」と書いてあるだけである。検索の要約は
「history は親しか返さない」と言い切るが、**その一文は原文に無い**。だから測った。

| 測ったこと | 結果 |
|---|---|
| Slack に投稿した件数（親1・返信3） | **4 件** |
| `conversations.history` の件数の増分 | **+1 件** |
| `conversations.replies` が返した件数 | 4 件（**先頭は親**） |
| 返信のうち `history` にも出た件数 | **0 件** |

**返信は例外を出さずに落ちる。** 「金曜の夕方でいけそう？」だけが届いて、
そこで決まった「月曜に倒す」が丸ごと消える。件数が減るだけなので、受け取る側からは
「議論が無かった」と見分けが付かない——**この課題の目的語そのもの**である。

`conversations.replies` は**新しいスコープを要求しない**（`channels:history` のまま）。
権限を増やさずに塞げた。

### 「返信を持っている親」だけを見張ると、いちばん多い形を落とす

最初は `reply_count > 0` の親だけを見張ろうとした。**これは効かない。**

返信は**後から付く**。読んだ時点で返信ゼロだった投稿に、あとで議論が始まる。
そのとき親はすでに `oldest` より前にあり、二度と読まれない。

だから**読んだメッセージは全部見張る**。窓（`WATCH_LIMIT` = **20 本**）で頭打ちにして、
1実行あたりの `conversations.replies` の呼び出しを 20 回までに抑える
（Slack の Tier 3 は毎分 50+ なので余裕がある）。

### 位置は2本持つ。混ぜると本文を飛ばす

| 位置 | 何を指すか | どこに入るか |
|---|---|---|
| `cursors` | チャンネル本文をどこまで読んだか | `{チャンネル: ts}` |
| `threads` | **親ごと**に、返信をどこまで読んだか | `{チャンネル: {親の ts: 返信の ts}}` |

**返信の ts で本文の位置を進めてはいけない。** 返信は親より後の時刻を持つので、
進めると**親より後に投稿されたチャンネル本文を飛ばす**。

進める順番は本文と同じで、**LINE への送信が成功した後**。失敗した回で進めると、
その返信は二度と読まれない。

### 窓から落ちたことを、黙って済ませない

`WATCH_LIMIT` を超えた親は見張りから外れる。**外れた親に後から付く返信は二度と届かない。**
黙って落とすと、この発展が塞いだはずの穴が別の形で開き直すので、画面に出す。

```
スレッドの返信: 3 件（見張っているスレッド 20 本）
  見張りから外れたスレッド: 1788495546.216329（以後の返信は届きません）
```

取れなかったスレッドも同じ扱いにする。**位置を進めないので次回また試す**が、
鳴らさないと「返信が無かった」と読まれる。

### 発展のテストが、既存コードのバグを掘り当てた

`ts` を**文字列で**並べ替えていた。本物の `ts` は桁が揃っているので実害は出ていなかったが、
桁が違えば `"10" < "2"` になる。狂うのは並びだけではない——**`latest_ts`（＝次回の起点）まで
狂う**ので、位置が飛んで静かに取りこぼす。

見つけたのは返信の窓のテストである。窓は読んだ順に並ぶので、順序の狂いが目に見える形で出た。
**穴は、その穴を狙っていない場所から出てくる。**

### 重複は、壊す道具から見ると「2件一致」として現れた

返信を読むループを書いたとき、チャンネル本文のループをほぼそのまま写した。
その結果、**1箇所を狙ったはずのミューテーションが2箇所に当たり、どちらも壊せなくなった**
（`mutate.py` は置換先がちょうど1箇所でないと失敗にする）。

コピーを直すのではなく消した——`_walk` / `_in_order` / `_classify` に共通化して、
歩き方・並べ方・除外の数え方を1箇所にした。

## 「必要に応じて」を実装に落とす

要件の原文は「**必要に応じて**要約し」である。**常に要約する実装は要件と違う。**
要約は情報を落とす操作なので、落とす必要が無いときに落とすのはただの劣化になる。

| 入力 | 出す本文 |
|---|---|
| 0件 | 「投稿はありませんでした」。**それでも送る** |
| 少なく・短い（6件未満かつ600字以下） | **原文をそのまま**。要約しない＝Gemini を呼ばない＝課金しない |
| 多い or 長い | 要約。**要約だと明記して**送る＋**原文へのリンク**を付ける |

**0件でも送る。** 送らないと、通知が来ない日が「投稿が無かった」のか「動いていない」のかを
受け取る側から区別できない。

閾値の 600 文字は**こちらの都合の数字**であって LINE の仕様ではない。相手の上限を定数に置くと、
相手が変えた日に**正しい送信を拒む**側で壊れる。

## 課題7の逆問題——しかも順序が裏返る

Slack は本文を保存するとき `&` `<` `>` を HTML エンティティに変換する。
課題7では**送る側**だったので、読み返しの照合を成立させるために変換を再現した。
今回は**読む側**なので、逆に戻す。

**戻す順番が裏返る。**

| | 順番 | 理由 |
|---|---|---|
| 課題7（escape） | `&` を**最初**に | 後にすると `<`→`&lt;` で作った `&` を再度拾い `&amp;lt;` になる |
| 課題1（unescape） | `&amp;` を**最後**に | 先に戻すと、本文として書かれた `&amp;lt;` が `<` まで進み**書いていない文字が現れる** |

実データで効いた。Slack には `Drive &amp; Notion` と保存されていて、要約に渡す前に
`Drive & Notion` へ戻している。

## 表示名は引かない

`U0BQ48E7E3H` を名前に解決するには `users:read` が要る。このアプリのスコープは
`chat:write` と `channels:history` だけ（2026-08-29 実測）。

**引けないものを引けたように見せない。** 名前らしきものを捏造するより、ID のまま出すほうが正しい。

## 実測でわかったこと

### 1. 一覧に載ることは、呼べることの証拠にならない

`client.models.list()` に載っている `gemini-2.5-flash-lite` を呼んだら **404** が返った。

```
404 NOT_FOUND. This model models/gemini-2.5-flash-lite is no longer available to
new users. Please update your code to use models/gemini-3.5-flash-lite
```

**エラー本文が後継を名指ししていた。** だから `translate_error` は本文をそのまま載せる——
こちらで要約するとこの情報が消える。

採用したのは `gemini-3.5-flash-lite`（1.2秒）。`gemini-2.5-flash` も通ったが 3.0 秒だった。

### 2. 要約は、書いていないことを言う

**この課題でいちばん重要な発見。** プロンプトに「ログに書かれていないことは足さないでください」と
明示したうえで実機を流したところ、こうなった。

| 要約の記述 | 原文 | 何が起きたか |
|---|---|---|
| 「**Google** DriveとNotion」 | 「Drive & Notion」 | **「Google」を足した**。たぶん正しい推測だが、書かれていない |
| 「**田中の要望により**、資料は…DriveとNotionの両方に共有される」 | 資料共有の依頼は田中、`Drive & Notion` と言ったのは**鈴木** | **2人の発言を1つに畳んで、片方に帰属させた** |

1回目（dry-run）では出ず、2回目で出た。**非決定的に混ざる。**

テストでは絶対に出ない種類の穴で、実機で流したから見えた。プロンプトで禁じても防げない。

**対処は「要約を正しくする」ではなく「原文へ辿れるようにする」にした。**
目的は「見逃しを防ぐ」ことであって「要約を信じさせる」ことではない。要約がズレても、
受け取った人が原文に辿り着けるなら目的は果たせる。

```
▼ 原文（要約は入口です）: https://<workspace>.slack.com/archives/C0BQ.../p1788011312620209
```

`chat.getPermalink` は**スコープを要求しない**（課題7で公式リファレンスに当たって確認済み）ので、
権限を増やさずに足せた。**要約したときだけ**付ける——原文をそのまま送っているならリンクは冗長で、
「落とした先への入口」というリンクの意味が薄まる。

### 3. 「キーが無い」と「読めなかった」を同じ NG にしていた

照合器（`verify_summary.py`）を書いたあと、**それより前に書かれた記録**にかけたところ、
こう出た。

```
NG  通数が1つ増えた: 期待 '1' / 実際 '(送信後の通数を読めなかった)'
NG  読んだ件数: 期待 1 / 実際 10
```

**どちらも照合器のほうが間違っている。** 送信時にそんな失敗は起きていない——
記録に `usage_after` と `oldest` のキーが**無かった**だけである。`.get()` が `None` を返し、
それを「読めなかった」と解釈していた。

2つ目はもっと悪い。`oldest` が無いのを「初回（範囲指定なし）」と読んで、
**チャンネルの全件を数えて**記録の件数と比べていた。

直しかたが正反対のものを1つの表示に畳んでいた（前者は撮り直し、後者は API の調査）ので、
`in` で存在を見て分けた。

### 4. SDK は、使っていない機能の勧告を出す

`google-genai` は、ツールを1つも渡していないのに stderr へ
「automatic function calling は Chat.send_message で使え」という勧告を出す。
**実行画面は記事のスクリーンショットになる**ので、`AutomaticFunctionCallingConfig(disable=True)` で切った。

切れたことは**本物のクライアントで確かめた**。テストは `config` の値を見ているだけで、
SDK が何を印字するかは見ていない。

## 送る前に確かめる（課題10から）

push は**未友だち・ブロックの相手にも 200 を返す**。判別できるのは
`GET /v2/bot/profile/{userId}` が 404 を返すことだけで、専用の判定 API は無い。

止める理由（`blocks`）と伝えるだけの話（`notes`）に加えて、**確認に使った値そのもの**（`checked`）を出す。

```
  [確認] 宛先: 届く（プロフィールを取得できた）
  [確認] 残り通数: 193 通
  送信前の確認: 通過
```

最初は「送信前の確認: 通過」だけを出していた。**何を見て通過にしたのかが残らない。**
実行画面はこの課題の証拠になるので、見た値を出す。

`remaining` の `None` は**無制限**であって 0 ではない。0 は「上限はあるが使い切った」で
真逆の意味になる。混ぜると、ガードが**無制限のアカウントで送信を止める**。

## 状態ファイルは「分からなくなったら止まる」

位置を見失った実行は、チャンネルの全履歴を読み直して巨大な要約を作り、LINE へ送る。
無料プランは月200通、Gemini は呼ぶたびに金額が動く。

だから**壊れたファイルを「初回」と解釈しない**。読めなかったことを読めなかったと言って止め、
人に直させる。

| 状態 | 扱い |
|---|---|
| ファイルが無い | **正常**（初回） |
| JSON として壊れている | **エラー**。初回として続行しない |
| `cursors` が辞書でない | エラー |
| 位置が文字列でない | エラー（数値だと float 経由で別のメッセージを指す） |

書き込みは一時ファイルに書いてから差し替える。途中で落ちても元の内容が残る。

### 状態ファイルは git に入れない

`state.json` は `.gitignore` に入れてある。**`results.json`（実行の記録）とは性質が違う。**

| | 何か | git |
|---|---|---|
| `results.json` | その実行で何が起きたかの**証跡**。照合の入力になる | 追跡する |
| `state.json` | 次にどこから読むかの**実行時状態** | **追跡しない** |

追跡すると、新しいクローンが「**他人がどこまで読んだか**」を持って始まる。
その位置より前は二度と読まれない——**この課題の目的に真っ向から反する**。
コミットのたびに差分が出るノイズにもなる。

**気づく機会は最初の1回しかない。** 一度 `git add` してしまえば、以後は何もしなくても
追跡され続ける。だから注意力に頼らず、`check_docs.py` の検査項目に入れてある。

## 使い方

```powershell
# 何を送るかだけ見る（送信しない・状態も書かない）
.venv\Scripts\python.exe task1\summarize_to_line.py --channel C0XXXXXXXXX --label "#general" --dry-run

# 実際に送る
.venv\Scripts\python.exe task1\summarize_to_line.py --channel C0XXXXXXXXX --label "#general" --json-out task1\results.json

# スレッドの返信も読む（発展）
.venv\Scripts\python.exe task1\summarize_to_line.py --channel C0XXXXXXXXX --label "#general" --include-replies --json-out task1\results.json

# 送った記録を別経路から突き合わせる（読むだけ）
.venv\Scripts\python.exe task1\verify_summary.py --results task1\results.json
```

### `--dry-run` が何をしないか

**送信だけをしない。** 読み取りは実行し、本文も組み立てて表示する。状態ファイルも書かない。
**Gemini は呼ぶ**（要約が必要な入力なら）ので、課金は発生する。

「dry-run」という語は何をしないかまで言っていない。ここに書いておかないと、
「何もしない」と読んで想定外の課金や書き込みに当たる。

## 照合には、原理的に届かない場所がある

LINE には bot が送ったテキストを読み返す API が無い（課題9で公式 OpenAPI 定義に当たって確認）。
**「送った本文が届いたか」は最後まで機械では言えない。**

この課題ではもう1つ増えた。**要約が正しいかは検証できない**（上の実測2）。

だから照合は**言えることだけ**を扱い、言えないことは「確認できない」と**必ず表示する**。
合格したときこそ表示する——全部 OK の画面に注記が無ければ、読んだ人は「全部確かめた」と受け取る。

| 言えること | どこから取るか |
|---|---|
| 通数が1つ増えた | `quota/consumption`（**押した経路とは別の口**） |
| 意図したチャネルへ送った | `/v2/bot/info` の `basicId` |
| 読んだ件数が再現する | Slack を**記録した `oldest` から**数え直す |

数え直しに現在の状態ファイルを使わないのは、位置が次の実行のために先へ進んでいるからである。
**物差しは記録の側から取る。**

## わざと壊して、テストが落ちることを確かめる

```powershell
.venv\Scripts\python.exe task1\tools\mutate.py
```

**テストが通っていることは、守られていることの証拠にならない。**
リポジトリを一時ディレクトリへ写し、**写した側だけ**を1か所ずつ壊す。

**69 か所すべて kill・素通り 0・置換先なし 0**（2026-09-04）。

「置換先なし」も失敗として数える。実装を直して壊しかたを直し忘れると、
**何も壊さずに全部通って「穴ゼロ」に見える**ため。実際 2 件出た（下記）。

### 最初は 6 件が素通りした。中身は 3 種類だった

| 素通りの理由 | 例 | 直した場所 |
|---|---|---|
| **テストが別の場所の文字列で満たされていた** | 「要約」見出しを消しても `assertIn("要約", body)` が通る——原文リンクの行に「要約は入口です」が入っているため | テスト（`"―― 要約 ――"` を見る） |
| テストが弱い | 空文字の `oldest`／一時ファイル経由であること | テスト |
| **ガードが冗長** | `needs_summary` の 0 件早期 return。外しても下の 2 条件が偽になるので結果が変わらない | **実装から消した** |
| **ミューテーションのほうが無効** | 書き換えても経路が変わらず、動作が 1 ミリも変わらない | `mutate.py` |

1つ目は課題9で踏んだ形と同じ（2つの assert が両方とも無関係な場所の文字列で満たされていた）。
**同じ穴が別の場所で開いた。**

4つ目が厄介で、**「テストが守っていない」と「壊せていない」は別の事実**なのに、
どちらも「素通り」として同じ行に出る。混ぜるとテストの穴を誤診して、
守られている場所に無駄なテストを足すことになる。

### 検査が本物を見つけたところ

資格情報の走査を書いたら、**テストのダミーを2件拾った**。

調べると、拾われた側（`common/tests/test_slack_auth.py`）は課題7の時点で
「本物の形を真似ない」と書いてダミーを作っていた。**悪かったのはこちらの網**で、
`xoxb-[A-Za-z0-9-]{10,}` が広すぎた。

直しかたは両輪にした。

| 直す場所 | 内容 |
|---|---|
| ダミー側 | 自分が書いた `AQ.this-must-not-appear`（本物の形）を `DUMMY-KEY-...` に変えた |
| 網の側 | 実測した本物の形に寄せた（Slack は数字・数字・英数字のハイフン区切り、Gemini は `AQ.` ＋40文字以上） |

**片方だけだと、本物を貼ってしまった日に気づけない。** 網が広いと毎回鳴るので無視するようになり、
ダミーが本物そっくりだと網を狭めた瞬間に本物も抜ける。

狭めたあと、**両方向を実測した**（値は出力していない）。

| 方向 | 結果 |
|---|---|
| 本物3種（`.env` の実物） | **3種とも検出** |
| ダミー4種 | **1件も誤検出なし** |

狭めた網が本物を捕まえることを確かめないと、「NG 0 件」は
「見つからなかった」ではなく「見ていない」を意味しうる。
