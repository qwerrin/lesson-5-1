## 2. 決めたこと

| 決定 | 理由 |
|---|---|
| **データ元は楽天市場の商品検索 API**（楽天ウェブサービス） | 公式・無料。ヒントがわざわざ「利用規約を確認しましょう」と言っている以上、**規約の外を叩かない**ことが要件の一部だと読む。記事は公開されるので、規約に触れる経路を選ぶと成果物そのものが問題になる |
| **Amazon をスクレイピングしない** | 上と同じ理由。**「やらなかった」ではなく「なぜやらないか」を規約の実文で示す**のを成果物に含める |
| **シートは履歴を追記する**（スナップショット上書きにしない） | ゴールの原文が「**定期的に**取得し反映する」。上書きだと「定期的に」が結果として残らない。追記なら価格の推移が成果物そのものになる |
| **`state.json` を作らない** | シートそのものが履歴なので、前回値もシートから読む。別ファイルに持つと「シートには入ったが state は進んでいない」というズレが構造的に生まれる。**情報源は1つにする** |
| **watchlist は `itemCode` 指定を基本にする** | `keyword` 検索だと日によって別商品が混ざり、価格の推移が別物同士の比較になる |

### 3.6 2026-09-08 の実測——**「見つからない」は 200 で返ってくる**

`fetch_items.py` を書く前に、`.env` の資格情報で3リクエスト投げた。
**この3つは公式ドキュメントのどこにも書かれていない。**

| 投げたもの | 返り |
|---|---|
| 正常（実在する `itemCode`） | HTTP 200 ・ `count=1` ・ `Items[0]["Item"]` に**ラッパで**入る |
| **実在ショップ ＋ 存在しない商品番号** | **HTTP 200 ・ `count=0` ・ `Items=[]`。エラーが1つも出ない** |
| 書式不正（`:` 無し） | HTTP 400 `wrong_parameter` / `itemCode is not valid` |
| 実在しないショップ | HTTP 400 `wrong_parameter` |

**2行目が 4-⑥ の実物。** 出品終了・売り切れ非公開・商品番号の打ち間違いは、
どれも「200 で0件」という同じ形で返る。**例外も 404 も出ない。**
ここを失敗として拾わないと、シートにはその日の行が**ただ無い**——
「価格が動かなかった」と読める。

一方、**ショップコードが違う打ち間違いは 400 で分かれる**。
「設定を直せば取れるもの」と「もう存在しないもの」は、この2つで区別できる。

**`itemCode` 検索は完全一致**（`count=1`）。だから `hits=1` で足りる。

**外側の形（ラッパ）は公式ドキュメントに書かれていない。**
書かれていないものは、変わっても告知されない。実装は平坦な形でも拾えるようにしてある
——固定すると、形が変わった日に**全商品が「見つからない」になる**（エラーは出ない）。

|---|---|---|
| 400 | `wrong_parameter` | パラメータ不正・必須不足 |
| 404 | `not_found` | データが見つからない |
| 429 | `too_many_requests` | リクエスト数超過 |

`unavailable_ip` = 0件）。要約ツールの出力ではなく、**ページを自分で引いて数えた**
——要約は情報源を混ぜることがある。

## 4. このシステムが取得していないもの

**「API が返さないから見えない」と「実装が見ていない」を分ける。**
前者は仕様の限界で、後者はこちらの責任。

| # | 見ていないもの | なぜ危ないか | 出どころ |
|---|---|---|---|
| 1 | `hits`×`page` の上限（3,000件）を超えた商品 | 3,001件目以降は「存在しない」のと同じ。**エラーは出ない** | 実装 |
| 2 | 同じ商品の**別出品** | 複数ショップが同一商品を出す。1つの `itemCode` だけ追うと「他店で最安値が下がった」を丸ごと見逃す | 実装（設計上の割り切り） |
| 3 | ~~**ポイント・クーポン・送料**~~ → **クーポンだけ** | `itemPrice` は本体価格。ポイント倍率で実質価格が大きく動く。「価格が変わっていない」と記録しても実質は下がっている | **訂正あり↓** |
| 4 | 在庫の**粒度** | `availability` は 0/1 のフラグ。「残り1個」と「100個」を区別しない | API |
| 5 | 取得しなかった時間帯の値動き | 1日1回なら、その間の値下げ→値戻しは**完全に見えない**。履歴が「動かなかった」と誤読される | 設計上の粒度 |
| 6 | 「売り切れ」「出品終了」「検索順位が下がった」の**区別** | どれも「レスポンスに出てこない」という同じ形になる | API |
| 7 | ~~API バージョン間のフィールド差~~ | ~~`20220601` と `20260701` で返るものが違う可能性~~ | **解消。** `20220601` は 400 で存在しない（3.2） |
| 8 | **申告した QPS の上限を超えたときの挙動** | 1 QPS で申告した。超えたら何が返るかを見ていない。`429` とは限らない | 未確認 |
| 9 | **送信元IPが変わったときの拒否** | 家庭用回線のグローバルIPはルータ再起動やISPの都合で変わる。変わった瞬間から全リクエストが拒否される。**「正常終了しても欠落する」ではなく「そもそも動かなくなるのに、定期実行だから誰も見ていない」** | 実行条件 |
| 10 | **認証の有効期限** | ⑨と同じ形。**OAuth を選んでいたら7日で死んでいた**（下記） | 実行条件 |

### 4-⑩ 認証の有効期限——OAuth を選ばなかった理由

Google の公式ドキュメントに明記がある（2026-09-06 確認）:

> A Google Cloud Platform project with an OAuth consent screen configured for an
> external user type and a publishing status of "Testing" is issued a refresh token
> expiring in **7 days**
>
> — <https://developers.google.com/identity/protocols/oauth2#expiration>

`lesson-4-3-2` の同意画面は **User Type = 外部・公開ステータス「テスト」**のまま。
課題1〜6 は**手で叩く単発スクリプト**だったので、失効しても同意し直せば済んでいた。
**課題2は「定期的に」動くことがゴールに書かれている。** 7日目に止まり、
**定期実行なので誰も見ていない**——⑨とまったく同じ形の穴になる。

**だから認証をサービスアカウントに変えた**（手順と採らなかった案は [`README.md`](README.md)）。
ブラウザの同意を経由しないので、この7日制限が無い。

> **移植したばかりの `common/google_auth.py` を、課題2では使わないと決めた。**
> 「置いてあるから使う」で選んでいたら、7日で死ぬ設計をそのまま通していた。
> 部品は共有部品として残り、テスト14件も回り続ける。
>
> **この⑩は、⑨を書いたから見つかった。** ⑨で「実行条件が変わると静かに死ぬ」という
> 分類を作ったので、認証を選ぶときに同じ問いを当てられた
> ——**分類を1つ作ると、次からその形の穴が見えるようになる。**

### 4-③ の訂正（2026-09-06・疎通確認の直後）

**着手前はこう書いていた**——「ポイント・クーポン・送料は API が返さないので**承知で残す**」。

**誤りだった。** 実物のレスポンスに `pointRate` `pointRateStartTime` `pointRateEndTime`
`postageFlag` `taxFlag` が入っている（3.4）。
根拠にしていたのは公式ドキュメントの「主なフィールド」13個で、**それを網羅だと思い込んでいた**。

| 項目 | 着手前の判定 | 実測後 |
|---|---|---|
| ポイント倍率 | 取れない | **`pointRate` で取れる。塞ぐ** |
| 送料 | 取れない | **`postageFlag` で取れる。塞ぐ** |
| 税 | （見ていなかった） | **`taxFlag` で取れる。塞ぐ** |
| クーポン | 取れない | **フィールドが無い。承知で残す**（42個の一覧に該当が無い） |

**「ドキュメントに載っていない」と「返らない」は別。**
課題1で学んだ「取得経路が返さないものは、エラーにならないので気づけない」の裏返しで、
今度は**返っているのに使っていなかった**。どちらも実物を見るまで分からない。

### 4-⑨ の訂正（2026-09-08・公式のエラー一覧を確認して）

**着手前はこう書いていた**——「拒否を他の失敗と区別して `理由=IP拒否` で記録する」。

**その形を確かめていない。** 公式のエラー一覧に 403 は無く、IP 拒否のエラー形も
載っていない（3.7）。「403 なら IP 拒否だろう」で固定語を埋めると、
403 が別の理由で返った日に**履歴へ嘘が残る**。

→ **載っていない状態は生のまま残す。** `不明(HTTP 403 <error>)` の形で
status と error 識別子をそのまま書く。実際に拒否を踏んだ日、その文字列が
シートに残る——**そこで初めて語を足せる。**

4-③ と同じ形の訂正である。あちらは「ドキュメントに載っていない＝返らない」と
思い込んだ誤り、こちらは「**載っていないものを、載っているかのように扱う**」誤り。
どちらもドキュメントの外側を、自分の推測で埋めようとしたときに出た。

**`error_description` は理由に入れない。** 楽天のエラー本文には URL が入りうる。
URL には `applicationId` が載る。本文をそのまま流すと、**鍵がシートにもスクショにも残る**。
記事には両方を載せる。

## 5. 正常終了しても欠落するケース

| # | ケース | 塞ぎ方 |
|---|---|---|
| A | `append` が**部分的にしか書けていない** | 返り値の `updates.updatedRows` と**送った行数を突き合わせる**。成功コードだけで信じない |
| B | 429 で退避して**諦めた商品が黙って抜ける** | **取得失敗も1行として記録する**（価格欄を空にして理由を書く）。「0件」と「取れなかった」を同じ無行にしない。課題1で「0件でも通知する」が評価された型をそのまま適用 |
| C | watchlist に入れたのに**一度も行が入らない商品** | 「安定して価格が動かない商品」と誤読される。watchlist の件数と、その回に書いた行数を毎回突き合わせる |
| D | シートのセル上限に当たる | 年単位で回すと当たる。**当たったときの挙動が未確認**なので、まず確かめる |
| E | **タイムゾーンの物差しが2本になる** | 取得時刻を UTC かローカルか**1本に固定し、列名にも明記する** |
| F | 商品名の改行・カンマで**セルが壊れる** | API は正常終了する。`transform.py` で正規化し、壊れる文字を含む名前でテストを1本置く |
| G | **前回が失敗行だった翌日**に比較する | 価格欄が空。空を 0 とみなすと「0円からの値上がり」「0円への値下がり」が必ず出る。**前回として採るのは `状態=取得` の行だけ**にし、無ければ「比較できない」と言う |
| H | 同じ `itemCode` のまま**商品の中身が差し替わる** | ショップは商品名も内容量も変えられる。価格の推移が別物同士の比較になるが、**API は正常終了する** |
| I | 取得時刻の**物差しが混ざる** | オフセット無しの時刻が1行混ざると、比較で例外が出るか、暗黙に別の物差しで比べる。5-E の裏側——書く側で1本にしても、**読む側が受け入れてしまえば崩れる** |
| J | 価格は同じで**在庫だけ 1→0 になる** | 「値段が動いていない」は正しいが、**買えない**。価格だけ見ていると「変化なし」と記録される |
| K | **見出し行が `COLUMNS` と一致している保証が無い** | 人はシートの列を並べ替えられるし、名前も変えられる。**追記は成功する**——列の意味だけが全部ズレる |
| L | `valueInputOption` の選択で**中身が変わる** | `USER_ENTERED` は文字列を数値・日付・数式に変換する（公式原文↓）。**取得時刻が日付に化けると、読み戻しが全滅する** |
| M | `insertDataOption` の既定 | `OVERWRITE` は「書き込む領域の既存データを上書きする」（公式原文↓） |
| N | **書いた型と読み戻す型が違う** | `values.get` の既定は `FORMATTED_VALUE`。公式の例では数値 `1.23` が **`"$1.23"` という文字列**で返る。`diff` は int しか価格と認めないので、**全比較が「価格が無い」になり、通知が永久に鳴らない**。エラーは出ない |
| O | watchlist の**重複** | 同じ `itemCode` が2つあれば2行入り、件数の突き合わせ（5-C）が狂う。API も2回叩く |
| P | watchlist が空・壊れている | 何も書かずに**正常終了**する。「今日は動いた」と読める |
| Q | **書いた列数と読み戻す列数が違う** | 末尾が空の列は返ってこない。15列で書いた行が**14列で戻る**。書き込みは成功しているので、**読み戻して初めて分かる** |
| R | **照合が0件でも「一致」と言える** | 0行と0行を比べれば必ず一致する。**比べていないことと、合っていることが同じ出力になる** |
| S | 書いたのと**同じ資格情報**で読み直す | 「書けたつもり」を「書けた」と確かめる経路が1本になる。権限の異常は、その1本が壊れたときに一緒に壊れる |
| T | **照合器そのものが検査されていない** | 課題1で実際に踏んだ。「素通り0」が「守られている」ではなく「**そこを見ていない**」を意味していた |
| U | 追記が**既存の行を壊していないか** | 追記した行だけ見ても分からない。上書きされた古い行は、**追記した行の検査を全部通る** |

### K〜P は書き込み層を書く前に出した（2026-09-08）／ Q は実機で出た

**ここは公式ドキュメントを読まないと1つも出てこない。** 実物を触っても、
`USER_ENTERED` で書いた日は普通に成功して、**壊れるのは読み戻す日**である。

原文（2026-09-08 取得）:

> **RAW** — The values the user has entered will not be parsed and will be stored as-is.
> **USER_ENTERED** — The values will be parsed as if the user typed them into the UI.
> Numbers will stay as numbers, but **strings may be converted to numbers, dates, etc.**
>
> — <https://developers.google.com/workspace/sheets/api/reference/rest/v4/ValueInputOption>

> **OVERWRITE** — The new data overwrites existing data in the areas it is written.
> **INSERT_ROWS** — Rows are inserted for the new data.
>
> — <https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/append>

> **FORMATTED_VALUE**（`values.get` の既定）— ... then `A2` would return `"$1.23"`.
> **UNFORMATTED_VALUE** — ... then `A2` would return the number `1.23`.
>
> — <https://developers.google.com/workspace/sheets/api/reference/rest/v4/ValueRenderOption>

| # | 塞ぎ方 |
|---|---|
| K | 書く前に1行目を読み、`COLUMNS` と**完全一致でなければ書かない**。空なら見出しを書く |
| L | `valueInputOption=RAW`。**解釈させない** |
| M | `insertDataOption=INSERT_ROWS` を明示する |
| N | 読むときは `valueRenderOption=UNFORMATTED_VALUE`。**書く側と読む側で型が変わらないことを、テストで留める** |
| Q | 読むときに幅を渡し、**末尾に落ちた空セルを補う**。ただし**長い行は切らない**——人が列を足したなら、それは `ensure_header` が弾くべき異常であって、読む側が隠してよいものではない |
| O | watchlist を読む時点で重複を落とし、**落とした件数を報告する**（黙って落とさない） |
| P | 空の watchlist は**エラーにする**。0件を正常終了にしない |

**Q は K〜P を全部やってから、実機で出た。** 設計の段階では出せなかった——
公式の記述（下記）は読めば分かるが、**どの列が末尾に来るかは実装を書いて初めて決まる**。
この課題では `理由` が末尾で、取得できた行では空になる。

> For output, empty trailing rows and columns will not be included.
> — <https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values>（2026-09-08）

**実装より先に穴を出す**やり方でも、**書いてからでないと出ない穴がある**。
だから出したあとも同じ問いを当て直す——「いま書いたこのコードは、何を見ていないか」。

**L と N は対になっている。** 片方だけ直しても、もう片方で型が変わる。
「書けたか」ではなく「**書いて読み戻したものが同じか**」で確かめる
——`verify_sheet.py` を別に置く理由もこれ。

### G〜J は `diff.py` を書く前に出した（2026-09-08）

A〜F は `transform.py` の前に出したもので、G〜J は**比較する層の穴**である。
同じ問いを層ごとに当て直すと、前の層では見えなかったものが出る。

**塞ぎ方は4つとも同じ形**——「言えないことを、言えないと書く」。

| # | 塞ぎ方 |
|---|---|
| G | 前回として採るのは `状態=取得` の行だけ。無ければ**「比較できない」を返す**。**「変化なし」にしない**——変化が無かったのか、比べられなかったのかは別のこと |
| H | 商品名の変化を**注意として併せて返す**。判定は止めない（表記ゆれで毎回鳴ると、本当の差し替えが埋もれる） |
| I | **オフセット付きの時刻だけを採用**し、読めなかった行数を数えて返す。0件になったことを「変化なし」と言わない |
| J | 在庫の変化も併せて返す。価格の判定とは**別の欄**にする |

**判定と通知を分ける。** 「いくら動いたか」は常に記録し、
**閾値は通知する側だけが持つ**。閾値未満を「変化なし」として記録すると、
後から見たときに「動かなかった日」に化ける。

### この分析で設計が1つ変わった

当初は「前回値はシートの末尾から読む」だけで足りると考えていた。
しかし **B と C を塞ぐには「今回 watchlist の何件を試して、何件書けて、何件落ちたか」が要る**。
シートに成功行しか書かないと、**落ちたものは行が無い＝見えない**。

→ **履歴シートに「取得できなかった行」も書く**（価格空欄＋理由列）。
情報源はシート1本のままで、B・C が同時に塞がる。`state.json` はやはり要らない。

### R〜U は `verify_sheet.py` を書く前に出した（2026-09-09）

**照合層は「照合したつもり」がいちばん危ない。**
下の4つは、どれも**照合が緑になったまま**成立する。

| # | 塞ぎ方 |
|---|---|
| R | **比べた行数とセル数を必ず報告し、0件は失敗にする。** 「一致」ではなく「N 行 × M セルを比べて一致」と言う |
| S | **読み取り専用のスコープで別に認証してから読む。** 書く側の資格情報を使い回さない |
| T | **`verify_sheet.py` 自身をミューテーションの対象に入れる。** 照合器を壊して、テストが落ちることを確かめる |
| U | 追記の**前後で全体の行数を数え、`前 + 送った数 = 後` を確かめる。** 一致しなければ、どこかが上書きされている |

**R がいちばん静かで、いちばん起きやすい。** 範囲の指定を1文字間違えるだけで
0行が返り、照合は「一致しました」と言う。**「一致」は「比べた」の証拠にならない。**

## 7. 構成（案）

```
common/
  google_auth.py    lesson-4-3-2 から移植（scopes 引数・token.json）
  sheets_client.py  シートの読み／追記のコア
  rakuten_auth.py   .env から applicationId / accessKey を読む
task2/
  fetch_items.py    楽天 API を叩く（間隔制御・429 の指数退避）
  transform.py      レスポンス → 行（正規化・欠損の扱い・壊れる文字）
  diff.py           履歴の末尾との比較（値下がり判定）
  to_sheet.py       CLI の皮
  verify_sheet.py   別経路でシートを読み直して照合
  watchlist.json    追う商品（itemCode）
  tests/ tools/
```

**資格情報は全部 `.env`。環境変数は使わない**（理由はリポジトリ直下の `.env.example` 冒頭）。
追加するのは `RAKUTEN_APPLICATION_ID` と `RAKUTEN_ACCESS_KEY`。

### シートの列

```
取得時刻(タイムゾーンを列名に明記) / itemCode / 商品名 / 本体価格 / ポイント倍率 /
実質価格 / 送料フラグ / 税フラグ / 在庫 / ショップ / レビュー平均 / レビュー数 /
URL / 状態 / 理由
```

**`状態` と `理由` が 5-B・5-C・4-⑥・4-⑨ を引き受ける。**
取れた行は `状態=取得` 、取れなかった行は `状態=失敗` ＋ `理由`
（`429` / `IP拒否` / `見つからない` / `不明`）。

**`実質価格` は計算列**（`本体価格` と `pointRate` から出す）。
生の値（`本体価格`・`ポイント倍率`）も必ず併記する——
計算式を後で変えたときに、**過去の行を計算し直せる**ようにするため。
計算結果しか残さないと、式を変えた瞬間に履歴の意味が変わって比較できなくなる。

`送料フラグ` と `税フラグ` は `postageFlag` / `taxFlag` をそのまま入れる。
**意味の解釈（0が送料込みか別かなど）は実装時に公式で確認する。**
確認するまで、列名を「送料込み」のような**解釈済みの名前にしない**。
