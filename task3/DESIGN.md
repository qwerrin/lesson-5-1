# 課題3 設計 — Google Meet 録音データから議事録を作成して Google ドキュメントに保存

**この文書は実装より前に書いた。** コードは1行も無い段階で、
「何ができるか」ではなく **「何を見ていないか」** を先に出すために置いている。

課題2 に続いて2回目になる。根拠は課題1（Slack → 要約 → LINE）の講評:

> 次回は今回身についた「何ができるかではなく、何を見ていないか？」という視点を、
> ぜひ開発の最初にも使ってみてください！
> 次の課題では要件定義やテスト設計の段階で、「このシステムが取得していないものは何か？」
> 「正常終了しても欠落するケースはないか？」を一度考えてから実装してみましょう。

**課題3 はこの視点が特に効く。** 音声は、欠けたことが出力に出ない入力だからである。
文字が化ければ読めば分かる。**音が録れていなければ、文字起こしは何事も無く短い結果を返す。**

## 2. 決めたこと

| 決定 | 理由 |
|---|---|
| **音声素材は自作台本を TTS に読ませて作る。他人の録音を使わない** | 探した結果、**日本語 × 会議形式 × 再配布可**を同時に満たす素材が見つからなかった（下記）。記事は公開されるので、**権利が不明な素材の中身を載せると成果物そのものが問題になる**。課題2 で「規約の外を叩かない」と決めたのと同じ判断 |
| **台本は自分で設計する**（自然な会議の録音を目指さない） | 素材を作れるということは、**穴を実物で試せる**ということ。5章に並べた欠落を、机上ではなく実際の入力として仕込める。借り物の録音ではこれができない |
| **文字起こしと要約を1回のリクエストにまとめない** | まとめると中間成果物が残らない。議事録が変だったとき、原因が**聞き取り**か**まとめ**かを切り分けられなくなる。分ければ文字起こし全文が物差しとして残る |
| **要約は構造化出力で受ける**（自由文にしない） | 「決定事項」「TODO」「論点」を型で受ければ、**空だったこと**が分かる。自由文だと、何も決まらなかった会議と、決定を拾い損ねた出力が同じ見た目になる |
| **保存は Google Docs API ＋ OAuth（本人アカウント）** | サービスアカウントが作ったドキュメントは**本人のドライブに出てこない**。提出にはスクショが要るので、見えないと成立しない |
| **課題2 で OAuth を捨てた理由は、ここでは当てはまらない** | 課題2 は「テスト」状態の同意画面で**リフレッシュトークンが7日で失効**し、かつ定期実行なので誰も見ていない、という組み合わせが危なかった。**課題3 は手で叩く単発**で、失効すれば同意し直せば済む。*同じ制約でも、実行の形が変われば危険度が変わる* |
| **議事録はドキュメントを新規作成する**（既存への追記にしない） | 会議1本につき1ドキュメント。追記だと 5-H（二重処理）が既存の内容を壊す形で出る |

### 素材を探した結果（2026-09-11）

| 候補 | 判定 |
|---|---|
| note「議事録練習音声（どこかのIT企業）」 | 用途は合致（週次定例・複数話者・WAV 約5分）。**ライセンス記載なし・有料**。権利が不明 |
| 日本語話し言葉コーパス（CSJ） | 申請制・再配布不可。中身は**講演**であって会議ではない |
| Nexdata / Datatang の話者分離データセット | 商用利用可だが**有料の法人向け**。規模も用途に合わない |
| PIXTA の「会議」音声素材 | 有料。かつ会議の**環境音**であって、議事録にできる会話ではない |

**「無い」ことも実測の結果として残す。** 探さずに自作へ逃げたのではない。

## 3. 仕様：確定しているもの／まだ確認できていないもの

**この節を分けて書くこと自体が成果物。** 二次情報を仕様として実装に埋めない。

### 3.1 Gemini の音声入力（公式ドキュメントから・2026-09-11 取得）

| 項目 | 値 |
|---|---|
| 対応形式 | WAV / MP3 / AIFF / AAC / OGG / FLAC / MPEG / M4A / L16 / Opus / ALAW / MULAW / WebM |
| 最大長 | 1プロンプトあたり 9.5 時間 |
| inline data | **総リクエスト 20MB 以下**。超えたら Files API |
| トークン | **音声1秒あたり 32 トークン**（1分＝1,920） |
| 時刻の参照 | `MM:SS` 形式で特定箇所を指せる |

**この表がそのまま設計を1つ決めている。** 5分の会議を WAV（16bit / 44.1kHz / ステレオ）で
録ると約 50MB で、**20MB を超えて inline では送れない**。MP3 なら約 5MB で収まる。
*保存形式の選択が、通る経路そのものを変える。*

**「32 トークン/秒」は実測と一致した**（2026-09-11）。14.42 秒の音声が 462 トークンで、
1秒あたり **32.04**。公式の値をそのまま見積もりに使ってよい。

測り方は「**同じプロンプト文を音声なしでもう1回数えて、差を取る**」。
1回の応答が返した合計値だけを見ても、どこまでが音声でどこからが指示文かは分からない
——*同じ応答の中で値どうしを比べるのは、何も確かめていないのと同じ*。

### 3.2 Google Docs 側（`lesson-4-3-2` 課題2 で実測済み・合格した実装）

- `documents().create` に**本文を一緒に送っても反映されないまま成功が返る**。
  挿入は `batchUpdate` で別に行う（2段階）
- **空文字の `insertText` は 400 で弾かれる**。手前で止めて理由を出す
- 読み戻しは `documents().get`

**移植元は合格済みのコードで、書き直さない。** 新しく書くと
「新しい実装から期待値を作る」形になり、実機で1度通った知識が失われる
（`common/google_auth.py` を移したときと同じ判断）。

### 3.4 仕込んだ罠が1つも効かなかった（2026-09-11）

疎通用の台本には、5章の欠落を2つ仕込んでおいた。**両方とも突破された。**

| 仕込み | 対応する欠落 | 結果 |
|---|---|---|
| 「金曜の夕方で」→「やっぱり月曜に変更で」 | **5-B**（言い直し・撤回） | ❌ 罠にならず。「金曜から月曜に変更」と正しく拾った |
| 「発注は1500個で」 | **5-C**（数値の誤変換） | ❌ 罠にならず。1500 と正確に返した |

**これは「欠落が起きない」の証拠ではない。** 3行・14秒・2話者では、
そもそも間違えようがない。*罠を仕込んだつもりで、仕込めていなかった。*

**欠落は分量と混み具合から生まれる。** 本番の台本は
「5分以上 / 3話者 / 複数議題 / 発言の被り / 固有名詞と似た音の語」まで上げる（8章-2）。

## 4. このシステムが取得していないもの

**「入力に入っていないから見えない」と「実装が見ていない」を分ける。**
前者は素材の限界で、後者はこちらの責任。

| # | 見ていないもの | なぜ危ないか | 出どころ |
|---|---|---|---|
| ① | **画面共有の中身** | 決定が資料に映っていて、音声では「これで行きましょう」としか言っていない場合がある。議事録には「これで」しか残らない | 素材 |
| ② | **チャット欄** | **要件の原文が「録音データやチャットログをもとに」と言っている**のに、音声だけ処理すると丸ごと落ちる。しかも Meet のチャットは**会議終了で消える**（保存操作をしないと残らない） | 実装 |
| ③ | **発言者の名前** | 声で分けられても名前には結びつかない。「誰が引き受けたか」が TODO に書けない | 素材 |
| ④ | **参加者と欠席者** | 誰が聞いていたかは音に無い。**決まったことを知らない人**が特定できない | 素材 |
| ⑤ | **会議の日時** | 録音ファイルの中に入っていない。ファイルの更新日時は**コピーで変わる**ので録音日の証拠にならない | 実装 |
| ⑥ | **無言の合意** | 頷きは音にならない。「反対が無かった」と「賛成した」が区別できない | 原理 |
| ⑦ | 前回の決定・次回の予定 | 会議の外の文脈。「継続案件」の経緯が議事録から抜ける | 設計上の割り切り |
| ⑧ | **議題に上がらなかったこと** | 議事録は「話されたこと」しか持てない。**抜けた議題は、議事録を見ても抜けたと分からない** | 原理 |
| ⑨ | ~~聞き取りの**自信度**~~ | ~~返らなければ誤変換と正解が同じ顔で並ぶ~~ → **解消。** 迷った箇所を自分から申告する（3.3-4）。**ただし「自信あり」と言ったことが正しさの証拠にはならない**ので、5-C / 5-J の照合は残す | 実測で解消 |
| ⑩ | **録音されなかった時間** | 録音開始が遅れた冒頭、切れた末尾。**ファイルは正常に開けるし、文字起こしも成功する** | 実装 |

### ②は要件そのものが指している穴

要件の原文に「チャットログ」がある。**音声だけ実装して「できました」と言うと、
要件の半分を見ていないことになる。** ①〜⑩のうち、これだけは講座側が先に書いている。

## 5. 正常終了しても欠落するケース

| # | ケース | 塞ぎ方 |
|---|---|---|
| A | **同時発言で片方が落ちる** | 台本に意図的に被りを入れて、何が返るか実測する。塞げないなら「重なりは拾えない」と議事録の末尾に明記する |
| B | **言い直し・撤回を取り違える** — 「金曜で……あ、やっぱり月曜」 | **課題1 のスレッド見逃しと完全に同型。** 本文だけ見て決定を取り違える。台本に仕込んで、要約が後の発言を採ることを確かめる |
| C | **数字・固有名詞の誤変換** — 「1500個」が「1000個」に | 文字起こしは**自信ありげに成功を返す**。台本の正解と突き合わせて誤り率を出す |
| D | **録音が途中で切れている** | ファイルは開けるし文字起こしも通る。**音声の長さと、文字起こしが言及した最後の時刻**を突き合わせる |
| E | **無音・雑音だけのファイル** | 「（無音）」などを返して**成功する**。文字数が極端に少ない結果を成功として扱わない |
| F | **長い会議で要約が丸める** | 細かい決定が消える。エラーは出ない。決定事項の件数を文字起こし側からも数えて突き合わせる |
| G | **文字起こしが出力の上限で打ち切られる** | 入力は 32 トークン/秒と安いが、**出力は全文**になる。長い音声ほど上限に当たる。**打ち切られても成功で返る**ので、末尾が会議の終わりに対応しているかを見る |
| H | **同じ会議を2回処理して議事録が二重になる** | 音声ファイルのハッシュを記録して、同じものを二度書かない |
| I | **言語の誤判定** | 日本語の会議が英訳で返る。**成功はする**。出力の言語を検査する |
| J | **話者ラベルの取り違え** | A と B が入れ替わっても、文章としては自然で気づけない。台本の正解と突き合わせる |
| K | **要約が原文に無いことを足す** | もっともらしい TODO が生成される。**決定事項は文字起こしの該当箇所を併記させて、原文に含まれるか機械照合する** |
| L | `batchUpdate` が**部分的に成功する** | 送ったリクエスト数と、返った `replies` の数を突き合わせる。成功コードだけで信じない |
| M | **挿入位置の索引がずれる** | 複数の `insertText` を1回で送ると、先の挿入で後の索引が動く。**書き込みは成功し、順序だけが壊れる** |
| N | **読み戻しが書き込みと同じ資格情報** | 権限の異常は、その1本が壊れたときに一緒に壊れる（課題2 の 5-S と同型） |
| O | **照合が0件でも「一致」と言える** | 0 と 0 を比べれば必ず一致する。**比べていないことと、合っていることが同じ出力になる**（課題2 の 5-R と同型） |
| P | **要約の根拠が原文のどこか分からない** | 「決定事項」だけ見ても、それが会議で言われたのか要約が作ったのか区別できない。K の裏側 |
| Q | **照合器そのものが検査されていない** | 課題1 で実際に踏んだ。「素通り0」が「守られている」ではなく「**そこを見ていない**」を意味していた |

### G は音声課題に固有の形

課題1・2 の欠落は**入力側**で起きた（スレッドが返らない、見つからないが 200 で返る）。
G は**出力側**で起きる。1時間の会議は入力で約 115,200 トークンと安いが、
文字起こし全文はそれに見合う長さの**出力**になる。
*入力の上限を確かめても、出力の上限は確かめたことにならない。*

## 6. 塞ぐもの／承知で残すもの

| 判断 | 対象 |
|---|---|
| **塞ぐ** | 5-B / 5-C / 5-D / 5-E / 5-F / 5-G / 5-H / 5-I / 5-J / 5-K / 5-L / 5-M / 5-N / 5-O / 5-P / 5-Q ／ **4-②（チャットログ）は入力として受け取れる形にする**（要件が指しているため） ／ 4-⑤（日時）は**実行時に人が渡す**（推測しない） ／ 4-⑩ は 5-D と同じ検査で拾う |
| **承知で残す** | 4-①（画面共有）／ 4-③（発言者の名前。**台本で名乗らせることで代替**し、一般の録音では取れないと明記する）／ 4-④（参加者・欠席者）／ 4-⑥（無言の合意）／ 4-⑦（会議の外の文脈）／ 4-⑧（議題に上がらなかったこと）／ 5-A（**まず挙動を確かめる**） |
| **解消した** | 4-⑨（聞き取りの自信度）— 疎通確認で「迷いを申告する」ことが分かった（3.3-4） |

**「承知で残す」を議事録の本文に書く。** 読む人が「この議事録が何を含んでいないか」を
知らないまま共有されるのが、この課題でいちばん危ない出口である。

## 7. 構成（案）

```
common/
  google_auth.py     OAuth（移植済み・Docs のスコープを渡す）
  gemini_client.py   既存（音声が通るかは 3.3-1 で確認）
  docs_client.py     ドキュメントの作成／挿入／読み戻し ← lesson-4-3-2 から移植
task3/
  transcribe.py      音声 → 文字起こし（形式・サイズ・出力上限の扱い）
  minutes.py         文字起こし → 議事録（構造化出力・根拠の併記）
  to_doc.py          CLI の皮（日時・参加者・チャットログを受け取る）
  verify_doc.py      別経路でドキュメントを読み直して照合
  meeting/
    script.md        台本（正解データ。話者・決定事項・仕込んだ罠）
    chat.txt         チャットログ（4-② 用）
    *.mp3            音声 ※ .gitignore
  tests/ tools/
```

**音声ファイルは追跡しない。** 台本（`script.md`）は追跡する——
**正解データが無いと 5-C / 5-J の照合ができない。**

### 議事録の構成

```
会議名 / 日時（人が渡す） / 参加者（人が渡す）
1. 決定事項（各項目に、文字起こしの該当箇所 MM:SS を併記）
2. TODO（担当・期限。担当が取れなければ「不明」と書く）
3. 論点（結論が出なかったもの）
4. この議事録が含んでいないもの（6章の「承知で残す」をそのまま出す）
5. 生成元（音声ファイル名・長さ・ハッシュ・モデル名・生成時刻）
```

**5 を入れる理由は 5-H と 5-G。** 二重処理と打ち切りは、
**議事録の本文だけ見ても絶対に分からない。**

## 8. 実装の順序

**骨組みを先に建てない。**

1. ~~**疎通確認を先に投げる。**~~ **2026-09-11 に完了**（3.3）。4件決着・モデルは据え置き
2. **台本を書く。** 5-B / 5-C / 5-J の罠を仕込み、**正解を別に書いておく**。
   **疎通用の3行では罠が1つも効かなかった**（3.4）ので、この水準まで上げる:
   **5分以上 / 3話者 / 複数議題 / 発言の被り / 固有名詞と似た音の語 / 数値の言い直し**
3. TTS で音声を作る（形式は 3.1 の 20MB 境界から決める）
4. `transcribe.py` — 差し替え可能な形で外部呼び出しを閉じ込める
5. `minutes.py` — 構造化出力。**根拠（MM:SS）を必ず持たせる**
6. `docs_client.py` ＋ `to_doc.py`
7. `verify_doc.py` — **書いた API ではなく読む API で**読み直して照合する
8. スクショ

## 10. 検算の方針

課題1・2 で評価された型を維持する:

- テストが緑であることを結論にしない。**わざと壊して、落ちることを確認する**（ミューテーション）
- **文章とコードを機械照合する**（`tools/check_docs.py`）。この DESIGN.md の数値も対象に入れる
- 成果物（ドキュメントの実物）で確かめる。API の戻り値だけで「入った」と判断しない
- **台本という正解データを持っているので、文字起こしの精度を主観で語らない**
