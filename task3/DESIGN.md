## 2. 決めたこと

| 決定 | 理由 |
|---|---|
| **音声素材は自作台本を TTS に読ませて作る。他人の録音を使わない** | 探した結果、**日本語 × 会議形式 × 再配布可**を同時に満たす素材が見つからなかった（下記）。記事は公開されるので、**権利が不明な素材の中身を載せると成果物そのものが問題になる**。課題2 で「規約の外を叩かない」と決めたのと同じ判断 |
| **台本は自分で設計する**（自然な会議の録音を目指さない） | 素材を作れるということは、**穴を実物で試せる**ということ。5章に並べた欠落を、机上ではなく実際の入力として仕込める。借り物の録音ではこれができない |
| **文字起こしと要約を1回のリクエストにまとめない** | まとめると中間成果物が残らない。議事録が変だったとき、原因が**聞き取り**か**まとめ**かを切り分けられなくなる。分ければ文字起こし全文が物差しとして残る |
| **要約は構造化出力で受ける**（自由文にしない） | 「決定事項」「TODO」「論点」を型で受ければ、**空だったこと**が分かる。自由文だと、何も決まらなかった会議と、決定を拾い損ねた出力が同じ見た目になる |
| **保存は Google Docs API ＋ OAuth（本人アカウント）** | サービスアカウントが作ったドキュメントは**本人のドライブに出てこない**。提出にはスクショが要るので、見えないと成立しない |
| **課題2 で OAuth を捨てた理由は、ここでは当てはまらない** | 課題2 は「テスト」状態の同意画面で**リフレッシュトークンが7日で失効**し、かつ定期実行なので誰も見ていない、という組み合わせが危なかった。**課題3 は手で叩く単発**で、失効すれば同意し直せば済む。*同じ制約でも、実行の形が変われば危険度が変わる* |
| **議事録はドキュメントを新規作成する**（既存への追記にしない） | 会議1本につき1ドキュメント。追記だと 5-H（二重処理）が既存の内容を壊す形で出る |

### 素材を探した結果（2026-09-11）

| 候補 | 判定 |
|---|---|
| note「議事録練習音声（どこかのIT企業）」 | 用途は合致（週次定例・複数話者・WAV 約5分）。**ライセンス記載なし・有料**。権利が不明 |

## 3. 仕様：確定しているもの／まだ確認できていないもの

**この節を分けて書くこと自体が成果物。** 二次情報を仕様として実装に埋めない。

### 3.1 Gemini の音声入力（公式ドキュメントから・2026-09-11 取得）

| 項目 | 値 |
|---|---|
| 対応形式 | WAV / MP3 / AIFF / AAC / OGG / FLAC / MPEG / M4A / L16 / Opus / ALAW / MULAW / WebM |
| 最大長 | 1プロンプトあたり 9.5 時間 |
| inline data | **総リクエスト 20MB 以下**。超えたら Files API |
| トークン | **音声1秒あたり 32 トークン**（1分＝1,920） |
| 時刻の参照 | `MM:SS` 形式で特定箇所を指せる |

**この表がそのまま設計を1つ決めている。** 5分の会議を WAV（16bit / 44.1kHz / ステレオ）で
録ると約 50MB で、**20MB を超えて inline では送れない**。MP3 なら約 5MB で収まる。
*保存形式の選択が、通る経路そのものを変える。*

**ただしこの計算は、実際に作る素材には当てはまらなかった**（2026-09-12）。
Windows の TTS は **16kHz / mono / 16bit** で出す＝**32,000 バイト/秒**なので、
5分で **9.6MB**。**WAV のまま inline で通る**し、20MB に当たるのは**約 10.4 分**である。
*一般論として正しい見積もりが、手元の素材には効かない。*
**20MB 境界（3.5-#2）は、この本番素材では踏めない**ので、境界の実挙動は
**別に長い捨て音声を1本作って**確かめる。

**「32 トークン/秒」は `count_tokens` とは一致する。しかし課金される側は 25 である**
（2026-09-12 に決着。詳細は 3.5-#6）。**見積もりに公式の値をそのまま使うと 28% 多く見る。**

測り方は「**同じプロンプト文を音声なしでもう1回数えて、差を取る**」。
1回の応答が返した合計値だけを見ても、どこまでが音声でどこからが指示文かは分からない
——*同じ応答の中で値どうしを比べるのは、何も確かめていないのと同じ*。

### #6 の決着：2つの API が違う率で音声を数えている（2026-09-12）

**`config` は関係なかった。** 音声の長さを6通りに変えて `count_tokens` で数えた:

| 秒 | 音声ぶん | ／秒 |
|---|---|---|
| 5.00 | 160 | 32.00 |
| 15.00 | 480 | 32.00 |
| 30.00 | 961 | 32.03 |
| 60.00 | 1,921 | 32.02 |
| 150.00 | 4,800 | 32.00 |
| 312.00 | 9,984 | 32.00 |

最小二乗のあてはめは **音声ぶん = 32.00 × 秒 + 0.5**、残差は ±1 トークン。
**`count_tokens` は公式どおり 32 トークン/秒**で、固定費は無い。

いっぽう**実機（`usage_metadata.prompt_token_count`）は 25 トークン/秒**である。
312.38 秒の会議で入力 8,057、プロンプトだけが 247 なので、
音声は 7,810 ＝ **25.00 トークン/秒**。

| 何を数える API か | 音声の率 |
|---|---|
| `count_tokens`（見積もり） | **32 トークン/秒** |
| `usage_metadata`（**課金された側**） | **25 トークン/秒** |

**これで 3.5-#6 の「101 ズレ」が説明できる。**
疎通確認は 14.42 秒だった: **14.42 × (32 − 25) = 100.9 ≒ 101**。
*ズレは固定値ではなく、音声の長さに比例していた。*

#### 途中で立てた仮説は間違っていた

2点（14.42 秒で 462、312.38 秒で 7,810）だけを見て
「固定費 106 ＋ 24.7 トークン/秒」という式を立てた。**きれいに当てはまった。**

**2点は必ず直線に乗る。** 未知数2つの式に2点を入れれば、
どんな値でも残差ゼロで解ける——*当てはまったことは、説明が正しい証拠にならない*。
3点目（実際には6点）を取った時点で、固定費は 0.5 で、
分かれているのは**長さではなく API** だと分かった。

## 4. このシステムが取得していないもの

**「入力に入っていないから見えない」と「実装が見ていない」を分ける。**
前者は素材の限界で、後者はこちらの責任。

| # | 見ていないもの | なぜ危ないか | 出どころ |
|---|---|---|---|
| ① | **画面共有の中身** | 決定が資料に映っていて、音声では「これで行きましょう」としか言っていない場合がある。議事録には「これで」しか残らない | 素材 |
| ② | **チャット欄** | **要件の原文が「録音データやチャットログをもとに」と言っている**のに、音声だけ処理すると丸ごと落ちる。しかも Meet のチャットは**会議終了で消える**（保存操作をしないと残らない） | 実装 |
| ③ | **発言者の名前** | 声で分けられても名前には結びつかない。「誰が引き受けたか」が TODO に書けない | 素材 |
| ④ | **参加者と欠席者** | 誰が聞いていたかは音に無い。**決まったことを知らない人**が特定できない | 素材 |
| ⑤ | **会議の日時** | 録音ファイルの中に入っていない。ファイルの更新日時は**コピーで変わる**ので録音日の証拠にならない | 実装 |
| ⑥ | **無言の合意** | 頷きは音にならない。「反対が無かった」と「賛成した」が区別できない | 原理 |
| ⑦ | 前回の決定・次回の予定 | 会議の外の文脈。「継続案件」の経緯が議事録から抜ける | 設計上の割り切り |
| ⑧ | **議題に上がらなかったこと** | 議事録は「話されたこと」しか持てない。**抜けた議題は、議事録を見ても抜けたと分からない** | 原理 |
| ⑨ | ~~聞き取りの**自信度**~~ | ~~返らなければ誤変換と正解が同じ顔で並ぶ~~ → **解消。** 迷った箇所を自分から申告する（3.3-4）。**ただし「自信あり」と言ったことが正しさの証拠にはならない**ので、5-C / 5-J の照合は残す | 実測で解消 |
| ⑩ | **録音されなかった時間** | 録音開始が遅れた冒頭、切れた末尾。**ファイルは正常に開けるし、文字起こしも成功する** | 実装 |

### ②は要件そのものが指している穴

要件の原文に「チャットログ」がある。**音声だけ実装して「できました」と言うと、
要件の半分を見ていないことになる。** ①〜⑩のうち、これだけは講座側が先に書いている。

| # | ケース | 塞ぎ方 |

| H | **同じ会議を2回処理して議事録が二重になる** | 音声ファイルのハッシュを記録して、同じものを二度書かない |
| I | **言語の誤判定** | 日本語の会議が英訳で返る。**成功はする**。出力の言語を検査する |
| J | **話者ラベルの取り違え** | A と B が入れ替わっても、文章としては自然で気づけない。台本の正解と突き合わせる |
| K | **要約が原文に無いことを足す** | もっともらしい TODO が生成される。**決定事項は文字起こしの該当箇所を併記させて、原文に含まれるか機械照合する** |
| L | `batchUpdate` が**部分的に成功する** | 送ったリクエスト数と、返った `replies` の数を突き合わせる。成功コードだけで信じない |
| M | **挿入位置の索引がずれる** | 複数の `insertText` を1回で送ると、先の挿入で後の索引が動く。**書き込みは成功し、順序だけが壊れる** |
| N | **読み戻しが書き込みと同じ資格情報** | 権限の異常は、その1本が壊れたときに一緒に壊れる（課題2 の 5-S と同型） |
| O | **照合が0件でも「一致」と言える** | 0 と 0 を比べれば必ず一致する。**比べていないことと、合っていることが同じ出力になる**（課題2 の 5-R と同型） |
| P | **要約の根拠が原文のどこか分からない** | 「決定事項」だけ見ても、それが会議で言われたのか要約が作ったのか区別できない。K の裏側 |
| Q | **照合器そのものが検査されていない** | 課題1 で実際に踏んだ。「素通り0」が「守られている」ではなく「**そこを見ていない**」を意味していた |
| R | **台本どおりに読まれた保証が無い**（2026-09-12 追加） | 素材を自作したので台本を「正解」として使うが、**TTS が数字や固有名詞を読み違えたら、正解データのほうが先に壊れている**。文字起こしが正しくても不一致として出るし、逆に読み違いと聞き違いが偶然打ち消し合えば一致として出る。**音声を1回だけ人が聞いて台本と突き合わせ、確かめた事実を残す** |

### G は音声課題に固有の形

課題1・2 の欠落は**入力側**で起きた（スレッドが返らない、見つからないが 200 で返る）。
G は**出力側**で起きる。1時間の会議は入力で約 115,200 トークンと安いが、
文字起こし全文はそれに見合う長さの**出力**になる。
*入力の上限を確かめても、出力の上限は確かめたことにならない。*

| 回 | 引用 | 文字起こしの実際 |

| 1回目 | 「10月3日までに**ご**用意します」 | 「…までに用意します」（**「ご」を足した**） |
| 2回目 | 「10月3日まで用意します」 | 「…まで**に**用意します」（**「に」が抜けた**） |

**どちらも1文字。** 読んでも絶対に気づかないし、意味も変わらない。
*しかし「逐語引用」を名乗る以上、1文字違えば根拠として機能しない。*

| 特集 | 特集4 / **特許2** | **特許** |
| 試算 | **資産2** | **資産** |
| 販促 | **反則1** | — |

**5-K の照合が見ているのは「要約が文字起こしに忠実か」だけである。**
文字起こし自体が間違っていれば、**忠実であるほど誤りが固定される。**

*一貫性の検査は、正しさの検査ではない。*
これは課題2 の講評（11章）が言っていることそのもので、
**`verify_source.py`（台本＝ソースと照合）が要る理由**が実データで出た。

### 実行ごとに結果が違う

同じ文字起こしと同じチャットログで2回投げて、
**1回目はチャット由来の TODO を出し、2回目は出さなかった**。
決定事項の件数も 2件 / 3件 と揺れた。
*「1回動いた」は「毎回こうなる」の証拠にならない。*

## 14. 移植を機械で証明する（2026-09-13）

`common/docs_client.py` は `lesson-4-3-2/task2` の**合格済みコード**から
API 層をそのまま持ってきた。**書き直すと、実機で1度通った知識が失われる**
（3.2 の4つの挙動は、あの実装が実際に踏んで分かったこと）。

### 「そのまま」を主張で終わらせない

`common/google_auth.py` の移植では、docstring にこう書いた:

> 実装は diff の docstring 部分以外が空になることで確認している

**それは1回やった話で、いま成り立っている保証にはならない。**
移植先をあとから直せば静かに崩れる。*「移植した」と書いた文は、
書いた瞬間から古くなる。*

そこで `task3/tools/check_port.py` を書いた。`ast` で関数の位置を取り、
**元のソースの文字列そのものを切り出して比較する**。
`ast.unparse` は使わない——整形し直すので、空白やコメントの違いが消えて
**「同じに見える」ようになってしまう**。

確かめたこと（コピーを1文字だけ変えて実行した）:

| 変えたもの | 結果 |
|---|---|
| 移植した関数に空白を1つ足す | ✅ 検出（行数は同じまま） |
| 移植したテストのクラス行にコメントを1つ足す | ✅ 検出 |

**移植元が無い環境では「確かめられませんでした」と言って終了 1 を返す。**
*見つからないことを「一致」として扱わない。*

### テストも照合の対象にした（実際に踏んだから）

最初は実装だけ照合していた。移植したテストに一括置換をかけたとき、
**移植元と違う内容に書き換えてしまった**（`batch_update_calls` → `batch_calls`）。
実装だけ見ていたら素通りしていた。

### テストは本体だけ写しても移植にならない

2つのテストファイルを1つにまとめたら、**移植したテストの意味が変わった**。

`test_読むだけで書き換えない` は、こう書いてある:

> get 以外のメソッドを持たない偽物で通ることが、書き込まない証拠になる。

つまり**偽物の作りが証拠そのもの**である。`batchUpdate` を持つ偽物と
一緒にすると、**同じテストが何も証明しなくなる**。
→ 移植元と同じくファイルを分け、**偽物ごと移した**
（`test_docs_client.py` / `test_docs_client_read.py`）。

### 足したものは1つだけ

`ensure_insertable` と、それを通す `insert_text_checked`。
移植元では空文字の検査が**CLI 側**にあり、*ライブラリを直接呼べば素通りできた*。

**移植した `insert_text` は消さずに残してある**——消すと
「移植元と同じ」が言えなくなる。`check_port.py` の `ADDED` に
新規のものを列挙してあり、**そこに無いものが現れたら「こっそり書き足された」
として落ちる**。

## 15. ソース側の照合が、内部整合の検査を通ったものを落とした（2026-09-13）

**`minutes.py` が「問題なし」と返した議事録を、`verify_source.py` が落とした。**

```
引用照合: 8 件中 2 件が台本と一致
所見 7 件
```

13章で「一貫性の検査は、正しさの検査ではない」と書いたことの実証である。
*課題2 の講評（11章）が要求していたのは、まさにこの層だった。*

### 何が出たか

| 所見 | 中身 |
|---|---|
| `方の[試算→資産]を出` | **誤変換**が議事録に固定されている |
| `は特[集→許]の前` | **誤変換**（特集→特許） |
| `願い[いが増加]しま` | 文字起こしの「お願いいします」がそのまま |
| `でお[手配おが増加]願い` | 文字起こしが足した語 |
| `林の[ほう→方]から` ／ `藤が[押さ→抑]えて` | 表記ゆれ |
| 担当が「不明」 | 台本では**佐藤**。**5-J が担当の欠落として出た** |

**7件すべてが本物**である（誤検知は下記のとおり3種類つぶした）。

### 逐語一致を求めない

引用は **台本 → TTS → 音声 → 文字起こし** を通っているので、台本とは必ず少し違う。
`difflib` で**いちばん近い台本の箇所**を探し、*違う文字だけ*を出す。

**差分には前後2文字を添える。** 文字単位の差分だけだと「特集」と「特許」が
`集→許` になり、**どの語が変わったのか読めない**（共通の「特」が差分から落ちる）。

### 雑音を3つつぶした——雑音が多い検査は、本物を隠す

最初の実行では所見が8件出たが、**そのうち3種類は誤検知**だった。

| 誤検知 | 原因 | 直し方 |
|---|---|---|
| `…が欠落` の長いブロック | 隣り合う2行をつないだ候補の**全体**と比べていた | 一致した範囲だけを切り出す（`matched_span`） |
| `[千八百→1800]` | 台本は読み、議事録は表記。**どちらも正しい** | 正解データの `numbers`（`spoken` / `value`）で読みを表記へ寄せる |
| 担当「小林」vs「小林さん」 | 敬称 | `clean_owner` で落とす |

**`value` の意味を「議事録に出る表記」に直した**（`1800` → `1800個`）。
*持っている対応表を使わずに「違う」と言うのは、検査ではなく雑音である。*

### レポートが出せずに落ちた

最初の実行は所見を7件持ったまま `UnicodeEncodeError` で死んだ。
本文に使った `—`（em ダッシュ）が **cp932 に無い**ためである。

**所見を持っているのに出せずに終わるのが最悪。** 記号を cp932 にあるものへ変え、
さらに `say()` で握って*1文字化けても報告は出す*ようにした。
ただし**落ちない仕組みは、落ちない書き方の代わりにはならない**ので、両方やっている。

### この層でも見えないもの

**台本に無いことは、この検査でも見えない。** 画面共有・参加者・無言の合意は
台本にも音声にも無いので、照合しても出てこない（6章の「承知で残す」）。
*照合器を1段足しても、materials の外は見えないまま。*
